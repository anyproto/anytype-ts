## ACCEPT — change the plan

1. **Ownership of physical targets across accounts/profiles** (lens1-01, lens2-03, lens3-08, lens4-02). Store a non-secret key fingerprint (`sha256(key)` first 16 hex) in the registry record. Before heal/update/remove, read the installed entry, compare its key's fingerprint with the record; mismatch → status `conflict` ("Anytype in <App> is set up by another account or by hand"), touch nothing; offer Replace (explicit) or Forget. On connect, if an `anytype` entry exists that no record owns → the sheet says it will replace an existing Anytype entry (explicit). Test: A connects → B connects (replace) → A's check shows conflict and A's disconnect leaves B's entry intact — on the SAME temp home.
2. **Preflight before mutation; preserve working state on cancel/failure** (lens1-03, lens2-08, lens3-07/09, lens4-04). Per adapter define the commit point. Claude Desktop fallback: ask quit consent BEFORE writing the key file. Claude Code MCP route: gate on `claude --version` ≥ 2.1.327 (stdin support) before `remove`; if `add-json` still fails after remove → report exactly that the old entry was removed, keep the OLD key valid, go to manual (no argv fallback). Skill route: write the skill file (no secret) first, then settings; on settings failure remove only a skill file Anytype created. Old key is revoked only after the new delivery committed (already in plan — keep).
3. **Reconnect preserves grant + expiry** (lens1-02, lens2-12, lens4-07). Manage loads `grant` and `expireAt` for the record's `appHash` from `ListApps`. Reconnect reuses that grant and the same absolute `expireAt`. If the old key is gone or expired → open the connect form prefilled with the last known non-secret grant (store `grant` + `expireAt` in the registry record — they are not secrets) and require an explicit confirm.
4. **Truthful disconnect** (lens1-04). Track cleanup and revoke separately. Revoke failed → keep the row with a Retry action. Cleanup failed / something left (`left: 'entry' | 'extension'`) → say what is left and how to remove it. Already-revoked = success.
5. **Signed bundle is enforced, and its status is real** (lens1-05, lens2-07, lens3-01, lens4-01). Sharing one signed artifact across the three OS jobs: NOT required for the POC (note as follow-up).

## REJECT — do not change (reasons)

- **Compromised-renderer threat model** (parts of lens2-02/06): the renderer mints and holds keys already; a compromised renderer can exfiltrate them directly. Main-side checks are about correctness (stale port, wrong window), not containment of a malicious renderer.
- **Pending-operation tokens / trusted-confirmation protocol for restart** (lens2-06 part): the Restart click in our own UI is the consent; over-engineering for a POC.
- **Windows DACL verification / ReplaceFile ACL preservation** (lens2-05, lens3-07 parts): out of POC; note as a ship blocker for Windows.
- **One signed artifact shared by digest across OS jobs** (lens2-07, lens3-01, lens4-01 parts): signing per OS job with the same cert is acceptable for the POC; note as follow-up.
- **curl header in argv** (lens2-13 part): same-user processes can read `~/.claude/settings.json` anyway; not a new exposure.
- **New analytics opt-in** (lens2-14 part): app-wide consent governs all events.
- **Restore Codex Route C / keep README's "Your system" selector** (lens4-17, lens1-19 parts): POC scope cuts stay; keep them listed in §1.4 as explicit deferrals awaiting product sign-off. Claude Code default = Skill + API stays, labelled **provisional** (pending the eval).
- **Moving full self-heal out of the POC** (lens1-19 part): keep — it's cheap given the registry.
- **Restructure phases around "one packaged connection first"** (lens4-15/17 parts): keep the 4-phase split; but Phase 1's acceptance must include positive IPC tests (not only a stub rejection).
