Verified while adjudicating (in-memory probes against the worktree modules, scratchpad `p5r2adj/`; no repository file touched):
- `envFile.ts` accepts four inputs it should refuse:
  - `NOTES='it\'s a note⏎MCP_ANYTYPE_API_KEY=⏎end'` is classified as usable, and `setEnvVar` writes the key inside `NOTES`. `opensQuote` takes `\'` as the closing quote.
  - `'NOTES'='multi⏎MCP_ANYTYPE_API_KEY=⏎end'` passes too, because `ASSIGN_RE` doesn't match a quoted name.
  - `MCP_ANYTYPE_API_KEY=⏎SERVICE_TOKEN=${MCP_ANYTYPE_API_KEY}` passes.
  - `A=one\nB=two\r\n` comes back as all-CRLF, and `MCP_ANYTYPE_API_KEY=old\nA=1` gains a final newline after `A=1`.
- Hermes (local checkout `~/anytype/hermes-agent`) does three relevant things:
  - It loads `.env` with python-dotenv `load_dotenv` (`hermes_cli/env_loader.py`). Interpolation is on by default there, and `\'` is an escape inside single quotes.
  - Its own `save_env_value` writes plain `KEY=value\n` lines.
  - `_remove_mcp_server` pops an emptied `mcp_servers`, and `DEFAULT_CONFIG` has no `mcp_servers`. So `mcp_servers: {}` only comes from Anytype's own disconnect.
- `yamlFile.ts` has three gaps:
  - `mcp_servers: # existing setup` and `mcp_servers: null # keep this note` lose their comment on connect.
  - A port heal drops `# mine` from inside our entry.
  - A flow parent `mcp_servers: { github: { url: http://a } }` passes the round-trip guard, then is re-laid out over several lines, and so is a flow root.

  An empty flow `{}` with `flow = false` set before the insert serializes as a block (`mcp_servers:` plus our lines). With a comment (`{} # note`), the comment moves.
- The new JSON adapters use the same `setJsonPath` as Cursor and the other older adapters (`jsonFormat` → `modify` + `applyEdits` on our key path). jsonc-parser's `withFormatting` widens an insertion's format range to whole lines. A sibling that ends on the insertion line is therefore expanded, and a trailing `// keep` lands after `anytype`. The undo guard in J8 gives the expected verdicts:
  - pass: `{}`, `"mcpServers": {}`, pretty multi-line siblings, CRLF, in-place replacement;
  - fail: one-line siblings, trailing comments on the insertion line, compact files.
- `restoreKey` discards its write result. `fileEntry.apply` always writes, even an identical entry, so a failed config.yaml rename during a rotation is reachable. `fileEntry.installedFp` returns `null` (not installed) when `keyOf` gets no `.env` value, including when `.env` can't be loaded.
- OpenCode on a file that doesn't parse: `fileEntry.plan`'s load-error branch builds the manual plan without `targetPath`. The controller then sends `previewTarget: ''`, and the `changed` case only calls `portCurrent()`, which is a no-op while the port is unchanged.

## High

J1 **A failed Hermes rollback leaves the new key unconfirmed, never queued for revocation** (l1 P5-R2-02, SEC-02, l3 P5-R2-04).
- Scenario: a working Hermes connection (key A) is rotated. `writeKey` writes key B into `.env`, so the existing entry already resolves to B. The disk fills: the config.yaml rename fails, and the `restoreKey` write fails too, but its result is discarded (hermes.ts 181–193). `apply` returns a plain failure (301–303). The registry keeps only hash A, the popup releases B on close (flow.ts `releasePendingKey`), and Hermes ends up on a revoked key while A is installed nowhere.
- Fix, in hermes.ts only, reusing the existing unconfirmed-delivery path (the T5/U2/V10 pattern):
  - (a) `restoreKey` returns `true` only when a re-read of `.env` shows the new key is no longer bound: the fingerprint differs from the new key's because the previous value is back, our line is gone, or someone else's value is there. It retries once on `changed`, like `removeKey`. Any write or read error, or the new key still there, returns `false`.
  - (b) When the config write failed and `restoreKey` returned `false`, `apply` returns `{ ok: true, unconfirmed: true, running: false, method: 'config', nextStep: 'reloadServer', targetPath: pre.targetPath, observedInstalled: false, createdDirs: key.createdDirs }`. The service then stores B as a candidate next to A and revokes neither. The popup shows its waiting state and keeps B. The next check's `settleUnconfirmed` keeps whichever key Hermes really reads.
  - (c) Hermes gets its own `installedFp`. When `loadEnv` errors (unreadable, refused by `envFile`, unresolvable), it returns `'unreadable'` so settlement waits. Otherwise it delegates to the engine. An unreadable binding can never retire the installed key.
- Tests ("J1: …"):
  - From a working connection, reconnect with every rename after the `.env` rename failing with ENOSPC. The service reply is `unconfirmed`, the record holds hash A plus candidate B, `revokePending` is empty, and closing the popup at the boundary sends zero RevokeApp.
  - A later check with `.env` holding B promotes B and queues only A. With `.env` made unclassifiable instead, the check settles nothing.
  - Only the config rename fails: `.env` is back to its exact bytes, the reply is a normal failure, and B is released.

J2 **Hermes `.env` accepts plain lines only, and an edit touches only our line's bytes** (l1 P5-R2-04, l1 P5-R2-06, SEC-06, SEC-01 `.env` alias half, l3 P5-R2-02, l3 P5-R2-07, l3 P5-R2-09).
- Scenarios:
  - A single-quoted value with an escaped `\'` that continues onto further lines passes the multiline guard (envFile.ts 20–48). A `MCP_ANYTYPE_API_KEY=` line inside it receives the key, and the read-back "confirms" it.
  - A quoted name escapes the guard entirely.
  - `SERVICE_TOKEN=${MCP_ANYTYPE_API_KEY}` hands the new key to whatever reads `SERVICE_TOKEN`.
  - One `\r\n` makes `setEnvVar` rewrite every other line's ending (17, 99), and a file without a final newline gains one.
- Fix, in envFile.ts: per the final-round rule, refuse rather than parse more.
  - `envUsable` accepts a file only when all three conditions hold:
    - (1) Line endings are uniform: all `\n` or all `\r\n`, with no bare `\r`.
    - (2) Every line is blank, a comment (first non-blank character `#`), or exactly `NAME=VALUE`, with these constraints:
      - `NAME` is `[A-Za-z_][A-Za-z0-9_]*` at column 0 (one BOM allowed on line 1), with no `export` and no spaces around `=`;
      - `VALUE` is unquoted with no `'`, `"` or `\`, or is `'[^'\\]*'` or `"[^"\\]*"` closing on that line;
      - optionally followed by spaces and a `#` comment.
    - (3) No non-comment line other than a `MCP_ANYTYPE_API_KEY=` assignment contains the text `MCP_ANYTYPE_API_KEY`.
  - Anything else is `unsupportedForm`: read gives `null`, set and remove are refused, and the plan is manual with the `anytype_me` steps.
  - `setEnvVar` splices instead of rejoining the file:
    - it replaces only the text of the first matching line and keeps that line's ending;
    - it drops later duplicates together with their own endings, as `removeEnvVar` does;
    - when our variable is absent, it appends `(text && no final newline ? eol : '') + line + eol`.
  - Update the existing ".env: one line, the rest kept" test: its `export`/CRLF case becomes `unsupportedForm`.
- Tests ("J2: …"):
  - Each refused fixture: escaped quote, quoted name, `export`, `NAME = value`, the alias, mixed endings. The plan is manual with `MCP_ANYTYPE_ME_API_KEY`, apply is refused, and `.env` is byte-identical.
  - Hermes-style fixtures: LF, CRLF, no final newline, our line in the middle. After connect, the file equals the input with only our line replaced or appended. After disconnect, it equals the input.

J4 **An unresolvable `.env` path gets no key** (l1 P5-R2-03, SEC-03 and l3 P5-R2-06, the `.env` half).

## REJECT
- **l1 P5-R2-08** (OpenCode heals a `.jsonc` record after `opencode.json` appears). The heal rewrites only our own entry in the record's file, which is one of OpenCode's two config files, the one Anytype wrote, and it already holds the key. Nothing leaves its file and nothing is revoked. At worst the status reads "ok" while OpenCode may read the other file, which is medium. Which file OpenCode reads when both exist is unverified (research §2). H10 already binds apply and manual confirmation to the selected file.
- **l3 P5-R2-01** (a reloaded window's stale bind sends a probe to a released port). This is not new: a window that wasn't reloaded keeps the same stale status after another window disables the API, because no broadcast is sent. Phase 4 accepted that with main-side `liveApi` gates for heals (A1, B2). The key reaches another process only if something else binds the released port, which is the local-actor class the brief excludes. No file is written and nothing is revoked.
- **SEC-09** (gateway setup continues in an existing personal profile named `anytype`). It needs a personal profile with exactly the name anytype-hermes' INSTALL.md reserves for the bot. An existing `anytype` profile is most likely an earlier gateway attempt, and `&&` would stop that from finishing. The text is copy-only and follows INSTALL.md (settled in H5).
- **SEC-03 and l3 P5-R2-06, config half** (manual steps naming a `config.yaml` that resolves outside home). Hermes' entry holds only `${MCP_ANYTYPE_ME_API_KEY}`, never the key. The only key-bearing step targets `~/.hermes/.env`, which H2 and J4 validate.

After J1–J8, Phase 5 is accepted. The orchestrator reads the J1, J2 and J8 code. Gates: typecheck, lint with 0 errors, and tests at the baseline (90 pre-existing failures).
