Research date 2026-11-26/27. Local Claude Desktop: 6.28899.6 (macOS). Nothing was installed or modified; no config contents read.
Legend: [V] primary source (official doc / local inspection), [GH] first-hand GitHub bug report (anthropics/claude-code - the de-facto public Desktop tracker), [3P] blog/community, UNCONFIRMED = not verified.

## 1. Short answers
| Question | Answer |
|---|---|
| macOS: does `open x.mcpb` / shell.openPath route to Claude and show a dialog? | YES. [V] local Info.plist registers document types `dxt` + `mcpb` (CFBundleDocumentTypes "Desktop Extension"). [GH #67865 comment] a user on macOS 26.5 opened via "double-click, `open`, or Settings" -> main.log `Handling DXT/MCPB file: <path>` then (when working) preview dialog -> `Installing unsigned extension` -> `Successfully installed extension local.mcpb.<author>.<name> vX`. Cold-start (Claude not running) behaviour UNCONFIRMED (standard Launch Services open-document; expected to work). |
| Windows: does opening from another app work? | NOT RELIABLY. [GH #102035, Oct-Nov 2026, build 2.37337.1 MSIX] the MSIX package registers NO `.mcpb` file association (Settings > Default apps > by file type finds nothing); a 2026-11-24 comment confirms same for current users ("Select an app, Claude not offered"). But **starting `claude.exe` with the .mcpb path as argument works** ("Claude shows the install dialog and installs normally"). So `shell.openPath` on Windows is unreliable; Anytype must spawn claude.exe itself. [3P] andrewleech/claude-connector-installer does exactly this (resolves install path, spawns Claude with the file). |
| Dialog contents | Official: "opens an installation UI where the user reviews extension details and permissions, configures required settings, grants permissions, and completes installation" [V claude.com/docs/connectors/building/mcpb]. 3P: shows manifest `tools` list, button "Install" [3P classmethod]. Exact layout/wording of buttons UNCONFIRMED (no official screenshot text). |
| Unsigned file | Install is ALLOWED: log `[warn] Installing unsigned extension from ...`; installed record `signatureInfo.status: "unsigned"`; UI shows **"Developer: unknown"** [GH Govcraft/beankeeper-desktop#134 quoting Desktop; GH #70397 `can_install:true`]. A distinct blocking/"Install Anyway" prompt is only second-hand (UNCONFIRMED). Hard block ONLY if admin sets `isDesktopExtensionSignatureRequired=true` (default false) [V claude.com/docs/third-party/claude-desktop/extensions]. `mcpb sign` reportedly still yields `unsigned` for self-signed bundles [3P search summary, UNCONFIRMED] - do not rely on signing; expect "Developer: unknown". |
| Can user_config (API key) be pre-seeded? | NO documented way. Spec: sensitive fields are "masked and stored securely" (OS Keychain / Credential Manager / Linux keyring) [V MANIFEST.md, support art. 10949351]; `default` supports only `${HOME}`,`${DESKTOP}`,`${DOCUMENTS}` substitution [V MANIFEST.md]; a default on a sensitive field would put the secret in the manifest in plaintext. So the user would have to TYPE it. **Recommended: do not use user_config for the key; generate a per-user bundle with the key baked into `server.mcp_config.env` (plaintext in the extension dir) OR - better - have the bundled proxy read the key from a file/OS location Anytype writes (e.g. `~/.anytype/mcp-key` / Anytype app data) at startup so the .mcpb itself stays secret-free and re-keying needs no reinstall.** Non-sensitive `user_config` fields (e.g. port) can have defaults. |
| Appears without restart? | Yes as far as reported: after "Successfully installed" the extension appears in Settings > Extensions and its server is launched (3P classmethod: appears immediately, no restart step; support article only says restart "if tools aren't available"). Known flakiness: stale tool binding cleared by disable->enable or full quit+relaunch [GH #70397 comment]; Code-tab sessions sometimes omit connected extensions (#105887, open, Oct 2026); #109646 (Nov 13, open, 3P): extensions get no tools in a NEW chat until a tool permission is changed. So: plan "Test connection" + "if tools missing, toggle the extension or restart Claude" fallback copy. |
| Bundled binary stdio (no Node)? | Supported by spec (`server.type: "binary"`, `platform_overrides`, Desktop appends `.exe` on Windows) [V MANIFEST.md]. BUT: macOS Gatekeeper/quarantine/notarization of an embedded binary is unaddressed officially [3P: authors sign+notarize their binaries; `mcpb sign` does not notarize]; per-platform binaries bloat the bundle. **Prefer `server.type: "node"`: Desktop ships a built-in Node (runs via UtilityProcess "built-in node compatible") - official: "Included with Claude Desktop on macOS and Windows, so users need no separate runtime" [V]. A single esbuild-bundled index.js proxy needs no Node install and no signing.** |
| Windows config path | See section 3. Classic (Squirrel/exe): `%APPDATA%\Claude\claude_desktop_config.json`. Current installs are **MSIX** (package family `Claude_pzs8sxrjxfjjc`): file lives at `%LOCALAPPDATA%\Packages\Claude_pzs8sxrjxfjjc\LocalCache\Roaming\Claude\claude_desktop_config.json` (virtualised; `%APPDATA%\Claude` may transparently alias to it only when it pre-existed at install). |
| Official Linux Desktop? | YES, **beta**: Ubuntu 22.04+/Debian 12+, x86_64+arm64, apt repo `downloads.claude.ai/claude-desktop/apt/stable`, package `claude-desktop`, launched as `claude-desktop`; Fedora/Arch unsupported; no Computer Use/dictation [V code.claude.com/docs/en/desktop-linux]. No auto-update (apt). |

## 2. Details and caveats for the .mcpb route (all real, current, silent-failure class)
1. **Zip compression bug (Node 24.16 / yauzl)**: Desktop 1.12603.1 (Jun 2026) hung SILENTLY (no dialog, no error, log stops at `Handling DXT/MCPB file`) on any deflated entry larger than 16 KiB (Windows) / 64 KiB (mac/Linux) [GH #67865, root cause nodejs/node#62557, tracked #63487; confirmed on macOS 26.5 and Windows]. Workaround proven on both OSes: **pack with STORED (method 0, no compression) entries** (`zip -rX -Z store`); installs on broken and fixed builds alike. Issue closed "inactive" 2026-08-10 without an Anthropic statement - whether current Desktop (6.x/7.x) is fixed is UNCONFIRMED. Also #68734: bundles with any single file >~108 KB silently no-op'd on 1.12603.1 (closed as misfiled, status unknown). **Mitigation: Anytype generates the .mcpb itself - write the zip STORED, keep the proxy tiny (single bundled file, ideally <100 KB, no node_modules).**
2. **manifest `name` must equal the server's `serverInfo.name`** (undocumented): on mismatch the extension installs, shows enabled, tools/list succeeds, but the model never gets the tools and tools/call never fires [GH #70397 root-cause comment, 2026-06-23, Windows; spec doesn't require it]. The Anytype proxy must report `serverInfo.name` identical to manifest `name` (e.g. both `anytype`).
3. **Windows sensitive user_config bug** [GH #78296, Jul 2026, closed]: sensitive values injected as `__encrypted__:<ciphertext>` instead of plaintext. Another reason NOT to use sensitive user_config for the key. Also mcpb#244 (open): sensitive values displayed in plaintext in the extension settings env panel; mcpb#250: empty optional field passed as literal `${user_config.id}`.
4. **MSIX filesystem virtualisation** errors during install ("Private dir leaf redirects (junction/substitute-name plant)") on 1.25927.0 [GH #84199, Aug 2026, closed 08-25]; Squirrel->MSIX upgrade left extensions dir absent [GH #67843]. Windows install failures are the most common field problem; keep a manual fallback ("Settings > Extensions > Advanced settings > Install Extension...") and show it in Anytype's UI.
5. **Drag-and-drop / Install Extension regressions** recur (#68002 Jun, #102035 Oct 2026 on 2.37337.1: DnD falls into chat; "Install Extension..." no-op). Anytype should therefore not rely solely on one entry path; offer (a) auto-open, (b) "Reveal file" + one-line manual steps, (c) config-file fallback (section 3).
6. **Admin policy**: `isDesktopExtensionEnabled` (default became `false` ONLY on third-party/managed deployments - Bedrock/Vertex/gateway; "extensions are off on third-party deployments and allowed on standard deployments" [V claude.com/docs/third-party/claude-desktop/configuration-changelog, v2.37337.1 entry + earlier default-change entry]); `isDesktopExtensionSignatureRequired`; `isLocalDevMcpEnabled`. The Releasebot summary "extensions no longer load unless enabled" (2026-11-24) refers to those managed-config keys, not consumer installs. Detect "extension install blocked" in UI copy.
7. Extensions do NOT show in all surfaces equally: Chat + Cowork (local) yes; Code tab flaky (#105887); cloud Cowork never. Extensions in "Claude Desktop and Claude Code" per support docs but sharing with Code CLI's own MCP config does not happen - Claude Code needs its own `claude mcp add` (other report).
8. Installed extension files: mac `~/Library/Application Support/Claude/Claude Extensions/` and `extensions-installations.json` in the same dir [GH #25579 lists "Claude Extensions\" and "extensions-installations.json" under userData]; local dir shows `Extension State` and `extensions-blocklist.json` (blocklist fetched from Anthropic at start, "Successfully fetched blocklist ... with N entries").
9. No install deeplink: [GH anthropics/claude-code#105428, 2026-10-27, open] explicitly requests `claude://connectors/add?...` - i.e. it does NOT exist yet. Also no deeplink for .mcpb. Local app.asar routes seen earlier: only code/new, code/continue, claude.ai/new, cowork/... Re-check later; not a usable route today.
10. Updating: privately distributed .mcpb are NOT auto-updated ("users need to install updated .mcpb files manually") [V support art. 10949351]. Re-key/port change => regenerate and re-open the bundle (or use the key-file approach in section 1 to avoid reinstalling).
11. Windows `.mcpb` handling workaround command: find claude.exe via running process or `Get-AppxPackage *Claude*` -> `InstallLocation\app\claude.exe`, then start it with the .mcpb path [GH #102035 comment 2026-11-24, 3P connector-installer]. MSIX install location pattern: `C:\Program Files\WindowsApps\Claude_<ver>_x64__pzs8sxrjxfjjc\app\Claude.exe` [GH #26073]. The WindowsApps dir is not listable by non-admin; use PowerShell `Get-AppxPackage -Name Claude*` (PackageFamilyName `Claude_pzs8sxrjxfjjc`) or `shell:AppsFolder\Claude_pzs8sxrjxfjjc!Claude` activation (the latter AUMID form UNCONFIRMED; test). Old Squirrel build: `%LOCALAPPDATA%\AnthropicClaude\Claude.exe` [GH #84199 uses this path as the "older Squirrel" check].

## 3. Config-file fallback paths (per OS)
- macOS: `~/Library/Application Support/Claude/claude_desktop_config.json` [V local]. File is also rewritten by Desktop (holds prefs, `globalShortcut`, `coworkUserFilesPath`, `mcpServers`): merge only `mcpServers.anytype`, atomic write, keep a backup. Never write `url` entries (wipes `mcpServers`, anthropics/claude-code#37286). Restart (full quit) required.
- Windows classic (exe/Squirrel/MSI): `%APPDATA%\Claude\claude_desktop_config.json`.
- Windows MSIX (current default from claude.ai/download as of Feb 2026+): `%LOCALAPPDATA%\Packages\Claude_pzs8sxrjxfjjc\LocalCache\Roaming\Claude\claude_desktop_config.json` [GH #25579 (2026-02-13), #26073 (2026-02-16, still open), #67843]. Same dir holds `Claude Extensions\`, `developer_settings.json`, `logs\`. Behaviour: if a real `%APPDATA%\Claude` existed BEFORE the MSIX install, the app used it instead (comment in #26073: "depends if the computer previously had a non-MSIX version... only affects fresh installs") - so Anytype should: (1) detect MSIX via `Get-AppxPackage -Name Claude*` / existence of `%LOCALAPPDATA%\Packages\Claude_*\LocalCache\Roaming\Claude`; (2) write to the virtualised path when that folder exists, else `%APPDATA%\Claude`; (3) if both exist, prefer the MSIX one but warn; (4) glob `Claude_*` rather than hardcode the hash (hash `pzs8sxrjxfjjc` consistent but may vary - UNCONFIRMED). "Settings > Developer > Edit Config" opens the WRONG (real-AppData) file on MSIX.
- Linux (official beta): `~/.config/Claude/claude_desktop_config.json` [3P, consistent with Electron userData; official doc silent - UNCONFIRMED]. Secrets/sign-in use GNOME Keyring/KDE Wallet; without a keyring users re-sign-in each launch (official troubleshooting).
- Config-route stdio entry: `command` must be an absolute path to a binary/script (Desktop does not inherit shell PATH reliably; `npx` re-resolves deps each launch and can exceed the ~60 s init window [GH #68240 comment]). Prefer `node <abs>/anytype-mcp-proxy.js` ONLY if Node exists - otherwise ship a helper binary or use the .mcpb route (built-in Node).

## 4. Linux specifics
- Official app exists (beta, Debian/Ubuntu only) - [V code.claude.com/docs/en/desktop-linux]. Users on Fedora/Arch use community repackages (e.g. unofficial AppImages/AUR) - out of scope, unverified.
- `.mcpb` on Linux: Desktop registers NO `.mcpb` file handler, so double-click/xdg-open does nothing [3P docs.jmrp.io]; install via Settings > Extensions > Advanced settings > Install Extension... Extensions DO work on Linux Desktop: a user reports a locally installed MCPB extension connected on "Claude Desktop (Linux 4.29.0)" [GH #105887, 2026-10-29]. Official mcpb doc still says Desktop "runs on macOS (darwin) and Windows (win32)" (stale). Does `claude-desktop path/to/x.mcpb` (CLI arg) open the dialog on Linux? UNCONFIRMED - test; on Windows the arg route works (see above), Electron's second-instance/open-file handler suggests it may. Anytype Linux plan: try spawning `claude-desktop <file>`; else reveal file in file manager + show the 3-click manual path; config-file route as fallback.
- Linux manifest `compatibility.platforms` must include `linux` (omit field = all platforms).

## 5. Recommended Anytype flow (updates to the verified report)
1. Detect Claude Desktop: mac bundle id `com.anthropic.claudefordesktop` / `/Applications/Claude.app`; Windows `Get-AppxPackage -Name Claude*` (or `%LOCALAPPDATA%\AnthropicClaude\Claude.exe` for legacy); Linux `dpkg -s claude-desktop`/`which claude-desktop`.
2. Mint key (spaces + read/write + optional expiry); write it somewhere the proxy can read (per-user file under Anytype data dir) OR bake into bundle env.
3. Build `anytype.mcpb` at connect time: STORED zip, manifest 0.3, `server.type:"node"`, single bundled proxy file (<100 KB), `serverInfo.name == manifest.name == "anytype"`, `compatibility.platforms:["darwin","win32","linux"]`, NO sensitive user_config (or optional non-sensitive `port` with default). Write to temp dir (no quarantine xattr since not downloaded).
4. Launch: mac `open -a Claude file.mcpb` (or shell.openPath); Windows spawn `claude.exe "<file>"` resolved via AppxPackage; Linux try `claude-desktop "<file>"` else manual.
5. UI copy: "Claude will ask you to confirm: click Install. It may say Developer: unknown - that is expected." Then "Test connection" (initialize against `/mcp/large` with the key) and a hint: "If Claude does not show Anytype tools, toggle the extension off/on or restart Claude."
6. Fallbacks (show only if the auto-open produced no installed extension after ~N s - detect by presence of extension id `local.mcpb.<author>.anytype` in `extensions-installations.json`/`Claude Extensions` dir): manual "Install Extension..." steps; then config-file merge route (per section 3).
