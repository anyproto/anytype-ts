**Operation / held keys** (flow.ts)
- One module-level `operation` `{ accountId, pending, committed, inFlight, cancelRequested }`. `ensureOperation()` creates it, stamped with the current account. `inOperation(fn)` registers the run as `inFlight` before its first await (one at a time, otherwise `busy`). `requestCancel()` sets `cancelRequested` synchronously (popup onClose); `releasePendingKey()` (unmount) still awaits `settle` and drops pending.
- `pending` = minted and undelivered (revoked on release). `committed` = delivered, or handed to main as unconfirmed (never revoked here). Each `HeldKey` carries the name/grant/expireAt it was minted with.
- `alive(op)` = not cancelled AND `accountId()` == `op.accountId`; checked after every await and before every account RPC. `mintPending` re-checks it after `dropPending`; `mintKey(app, account)` refuses when another account is signed in; `hashOf(key, account)` looks up only under that account.
- A key minted but not identified (late CreateApp, account switch, lookup exhausted) → `releaseUnknown` / `remember(account, '', key)`: module `leftovers` hold `{ accountId, hash | key, attempts }` (key only until it is looked up; memory only). `checkOnce` of that account looks it up, revokes, or registers an orphan. `cleanupFailed()` is true for the current account while a leftover failed or is still unidentified (the page's Local API hint).
- Committed `aiConnectApply` / `aiConnectRecordManual` replies under a changed account: `commit(op)` first (key kept), then `CANCELLED` / `reason: 'cancelled'` — no store upsert, no revoke, no probe; the old key waits for its own account's next check. `probeDelivered` refuses another account.
- `plan()` returns `{ plan, port }` (the port it was requested with). `connectIn` compares that port right before apply.
- `revocable(c)` excludes running candidates unless `c.removed` (V10). `stillSaving(c)` (store copy first): a running candidate → no manual rotation (reconnect, Create key, "I've updated" all refuse, W5).
- `checkOnce`: `ensureAccount` first; `moved()` before every revoke (also after a failed one); a failed check sets `loadFailed` (W15); after a successful check, hashes the check made revocable (a promoted candidate's retired key) are revoked once in the same pass (W9).

**Manual setup contracts** (flow.ts)
- `ManualInput` gains `port` (the manual plan's port: mint and record only for it), `reread` (a reconnect's old key access, re-read before mint and before record), `replace` (Claude's foreign key file shown), and `connectionId` is sent for every existing record (W10).
- `ManualResult` `{ ok: false, reason?: 'stillSaving' | 'changed' | 'grantChanged' | 'cancelled', access? }`; ok carries `probe`. `CreateManualResult` adds `grantChanged` and `stillSaving`; `ok`/`pending`/`plan` carry `plan` + `port` (Other app shows the fresh plan's steps).
- `ReconnectResult` adds `stillSaving`; `manual` carries `{ plan, port, access }` — the manual branch (`reconnectManual`) mints only with a fresh `manualUsable` plan at the target Manage showed, else returns `{kind:'plan', reason:'manual'}`.
- Claude Desktop's `createManual` runs `connectIn({ manual: true, shown: fresh, replace })`; `connectIn` with `manual` requires `manualUsable(current)`, a `targetPath` and `shown` (bound `previewTarget`, W8).
- `retryProbe` → `RetryProbeResult` (`lookupFailed: true` for a failed lookup); prefers the op's committed key when it is the record's.

**Controller state machine** (controller.ts)
- `view`: connect | finish | manage | manual | unsupported; `initial()` picks it from `data` and the store.
- `phase` (finish): delivering, needsQuit, needsQuitSelf, installExtension, step, afterRestart, added, stalled, unconfirmed, error. `pollStopped` (unconfirmed wait ran out → Check again, `checkAgain()`). `manual.mode`: create | confirm | done | restoreOld | prerequisite; `manual.planPort`, `manual.probeFailed`.
- `this.attempt` is the approved delivery: `{kind:'connect', input}` built once in `submit()`, or `{kind:'reconnect', connection, opts}` from `reconnect()` (a manual record's carries Manage's plan). `deliver(consent)` merges consent; `handle()` maps results to views. A manual record stays manual through every continuation (`manualRecord()`).
