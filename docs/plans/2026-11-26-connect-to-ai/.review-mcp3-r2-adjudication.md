## High

S1 **A queued revocation is cleared only by heart's own answer, never by a transport error** (l2 SEC-01).
- Scenario: RevokeApp gets HTTP 400 from the grpc-web layer before heart handles it. grpc-web reports code 3, the dispatcher passes it as `error.code`, and `revokeApp` reads it as heart's NOT_FOUND. `aiConnectRevoked` or `aiConnectOrphan { done }` then drops the hash. The bearer stays valid, and nothing is left to retry it. This breaks §2.9: a revocation is dropped only on "success or not found".
- Fix:
  - `dispatcher.ts`: the transport-error branch adds `transport: true` to the error object it passes. This is additive; no other caller reads it.
  - `flow.ts revokeApp`: `message?.error?.transport` → `'failed'`. Only a decoded reply with no code (`'ok'`) or with code 3 (`'notFound'`) clears the hash.
- Tests ("S1: …"):
  - `dispatcher.sentinel.test.ts`: a service error `{ code: 3 }` reaches the callback with `transport: true`.
  - Renderer: RevokeApp answers a transport error with code 3. The hash stays in `revokePending`, no `aiConnectRevoked` is sent, and the next check calls RevokeApp again. A decoded heart error with code 3 clears it.

S2 **Reconnecting a Command record whose key is gone delivers what the form shows, as Command, to the same record** (l1 P3-R2-01).
- Scenario: a Command record's key expired. Reconnect → `needsForm` → the form, prefilled. The user picks read-only, one space and 30 days, then submits. `this.method` was never set on this path, so `submit` sends the URL setup. That path reloads the record's stored grant over the user's edits. heart mints read-write, all spaces, `expireAt: 0`: broader access than the sheet showed.
- Fix (`controller.ts prefillReconnect`): when `r.connection.method == 'command'`, set `this.method = 'command'`, as `enterManual` already does. `submit` then sends `method: 'command'` with `existing` = that record. `flow.connect` plans and delivers by its id (the same `other-*`).
  - Key gone: `reread` is undefined (`controller.ts:520`), so CreateApp gets the form's grant, name and expiry.
  - Key present: the old grant is re-read as in the POC (`reread`, W4).
- Test ("S2: …", controller boundary): a Command record with an expired key. Reconnect, change the form to read-only, one space and 30 days, and submit.
  - Exactly one CreateApp is sent, with that grant and that `expireAt`.
  - `aiConnectApply` carries `method: 'command'` and the same `connectionId`.
  - No URL sheet opens, and there is still exactly one `other-*` record.

S3 **Intent recovery never revokes a key that a current record or a live mint may own** (l1 P3-R2-03, l2 SEC-03, l3 R2-01).
- Scenario: an earlier run left a `Cursor` intent. In this run:
  - (a) the user retries Cursor. heart has minted the key, but its CreateApp reply hasn't reached the renderer yet. Or:
  - (b) another window commits a new Cursor connection between this check's `aiConnectList` and its ListApps.
  - Either way, the check matches the new key by name and `createdAt >= time`, against a stale record snapshot. Main queues it, and the renderer revokes a working key.
- Fix (main is the authority; it already has the data):
  - The renderer's recovery call sends `aiConnectOrphan { accountId, hash, intentId }`.
  - Main's `orphan` refuses a recovery hash (`{ ok: false }`) when:
    - (a) it is the `appHash` of any record or candidate of that account now; or
    - (b) an intent of the same account and name is in `liveIntents`: a mint of this run whose CreateApp or delivery may still be in flight.
  - The renderer already keeps an intent whose orphan was refused (`queued = false`), so the next check decides again:
    - the hash is managed by then → no match → the intent is cleared;
    - the live mint ended → the old intent is resolved then.
  - Recovery still acts only on intents from earlier runs, which are older than any in-flight deadline.
  - The leftovers loop (released keys, no `intentId`) is unchanged.
  - Update the §13.2 "Mint intent" line.
- Tests ("S3: …", renderer + service):
  - An earlier-run `Cursor` intent. Hold the retry's CreateApp reply after heart created `hash-1`, and run a check: zero RevokeApp for `hash-1`, and the old intent is kept. Release the reply: Connect is `ok`, and the next check clears the old intent with no RevokeApp.
  - Hold the startup ListApps reply, complete a new Cursor connection, then release it: zero RevokeApp for the record's hash.

S4 **The Windows sign hook takes electron-builder's real callback arguments** (l1 P3-R2-02, l4 BLD-R2-01).
- Scenario: electron-builder signs `Anytype.exe` by calling the hook as `(configuration, packager)`. `sign.js` treats `packager` as `runner` and throws `TypeError: runner is not a function`. Every Windows tag and nightly fails after the forwarder was signed. This is independent of Q13.
- Fix (`electron/hook/sign.js`):
  - `exports.default = (configuration, _packager) => sign(configuration)`. This is the `CustomWindowsSign` shape, and `prepare-forwarder.js`'s single-argument call keeps working.
  - Runner injection moves off the parameter list: `sign` calls `exports.runner` (default `run`), which tests replace.
- Test ("S4: …"): replace `runner` with a stub. Call the exported default with an electron-builder-shaped pair (`{ path: 'Anytype.exe', site, hash, isNest, computeSignToolArgs }`, `{ appInfo: {} }`). The stub gets exactly one AzureSignTool call naming `Anytype.exe`, and nothing throws. The Q11 tests use the stub the same way.

S5 **The stable copy is handed out only when another OS user can't replace it and the kernel can run it** (l2 SEC-02, l3 R2-07; completes Q18).
- Scenario:
  - Windows: a restored or foreign `~/.anytype/bin` or `anytype-mcp.exe` grants another account Modify. `.anytype` and the item store are private, so heart passes, and the bytes hash right. The other account replaces the exe. The AI app then runs their code as the victim, with the victim's items. §0.2 puts other OS users in scope.
  - Linux: a home mounted `noexec`. The `0755` copy passes `startable()`, and the bundled helper writes the item. Setup reports success, and every client fails to start the command.
- Fix (`forwarder.ts`):
  - Windows: `ownDir(bin, false)` runs `protectNewDir` on a `bin` it creates (the user, SYSTEM and Administrators, protected, inherited by the copy written into it), as Q17 does for `.anytype`.
  - Windows: before `ensureInstalled` returns the path, on both the equal-hash path and the keep path, one PowerShell query reads the owner and the allow entries of `bin` and of the exe. Every SID must be the user's, `S-1-5-18` or `S-1-5-32-544`; otherwise the result is `installFailed`. There is no repair. A passing answer may be cached for the run: only an account that can already change the list could widen it, and this check refuses such an account.
  - POSIX: `startable()` also requires `env.canExecute(file)` (`fs.accessSync(X_OK)`, which honours `noexec` on Linux). Otherwise the result is `installFailed`, before any `key set`.
  - Update the §13.2 "Stable copy" line.
- Tests ("S5: …", fake env):
  - win32, `bin` missing: one icacls call with the Q17 grants.
  - win32, an existing `bin` whose ACL answer includes `S-1-5-32-545` with Modify: `installFailed`, no key verb, no command.
  - win32, an equal-hash exe with an extra SID: `installFailed`.
  - win32, owner and entries only the three: `ok`.
  - Linux: `canExecute` false for the stable path (but true for the bundled one): `installFailed`, zero `key set`.
  - The real Windows run is S12.

## Medium

S6 **A writer deadline survives Disconnect and a retarget, until the writer can no longer commit** (l1 P3-R2-04, l2 SEC-04, l3 R2-03; l1 P3-R2-06, l3 R2-04; extends Q3).
- Scenario:
  - Disconnect: a first `key set --expect absent` is still waiting on its lock (a restart, or an indeterminate timeout). Disconnect reads the item as absent, takes that as final, and drops the candidate's `until`. After the revocation, the record is deleted. The helper then writes the revoked key, and nothing retries it.
  - Retarget: a deferred `large → full` retarget. The first check reads the old revision and clears the intent. The helper commits `full`. The next check heals it back to `large`, with `nextStep: 'none'`.
- Fix (main's queue already serializes within a run; this covers a writer that outlived its verb):
  - (a) `remove()`: when any candidate is `stillRunning`, `removedRecord` is built `withItem`, so `itemDelete`, `itemFps` (with the candidates' fingerprints) and `itemUntil = max(until)` are kept. The revocation is queued at once, as today.
  - (a, cont.) In `check`, `deleteItem → owner: 'none'` clears `itemDelete` only when `!itemUntil || now >= itemUntil`. `deleted` and `foreign` clear it as today.
  - (b) `retargetJournal` saves `retarget: { port, tier, rev, until: now + verb timeout + 5 s }`.
  - (b, cont.) `take()` clears `rec.retarget` only when `res.item.rev >= rec.retarget.rev` (the expected revision, where Q19's restart rule applies) or when `now >= until`. Until then the existing "intent pending → the tier is not healed back" rule holds.
  - (a, b) The registry validator accepts `itemUntil` and `retarget.until`. Update the §13.2 "Bookkeeping as built" line.
- Tests ("S6: …", main):
  - Restart from the snapshot taken at `key set`. Disconnect with the item absent: the record stays `removed` with `itemDelete`, and the hash is queued. The fake then writes the item: the next check deletes it, and only then is the record removed. With no write and the deadline passed, the record goes.
  - Defer a Command retarget. A check at the old revision inside the deadline keeps the intent and writes nothing. The helper commits: the next check gives tier `full` and `nextStep: 'restart'`. With the old revision past the deadline, the intent is cleared and nothing is rewritten.

S7 **A config-route candidate keeps the entry it journaled, whatever the verb returns** (l1 P3-R2-05, l2 SEC-06, l3 R2-05; completes Q15).
- Scenario: Claude's manual setup (config route) → Create key. `key set` writes the item, then loses its receipt. `manualPrepare` returns an unconfirmed outcome without `configEntry` / `entryDigest` / `configPath`. `withCandidate` replaces the journaled candidate with it. Then:
  - the user pastes the snippet;
  - the check promotes the key and reports `removed`;
  - Disconnect leaves `mcpServers.anytype` in Claude's config.
- Fix (service, one place for every adapter): `withCandidate` takes `configEntry`, `entryDigest` and `configPath` from the candidate it replaces when the outcome lacks them.
- Test ("S7: …", main): manual config Create key; the fake writes the item and drops the receipt; the snippet is in Claude's config verbatim. The next check promotes the key with `entryDigest` and reports `ok`. Disconnect with Claude stopped removes the entry.

S8 **Claude config-route apply and removal are serialized across profiles** (l2 SEC-07, l3 R2-02; completes Q5).
- Scenario: profile A disconnects. It deletes its item and awaits Claude's process check. Meanwhile profile B, a separate process and registry, connects through the config route. A's final write checks only the digest, which is identical for both accounts, so it removes B's entry. B's item and record say connected, but Claude never starts the forwarder.
- Fix ("an operation lock per connection", across processes): export `withLock` from `forwarder.ts`, and hold it on `~/.anytype/ai-connect/claude-desktop.lock` (beside `items/`, never inside it) around:
  - `fallback.apply` and `manualPrepare`'s config branch, from the config merge through `key set`;
  - `claudeDesktop.remove`, from `deleteItem` through the config edit.
  - The 10 s wait and the 60 s staleness are those of the stable-copy lock; every verb ends within 30 s.
  - If remove can't take the lock, nothing is deleted: `itemLeft`, `left: 'entry'`, retried by the check.
  - If apply can't take it, the result is `write/changed`, before any item write.
  - Waiting for Claude to quit stays outside the lock.
- Test ("S8: …", main): two services on one fake home with separate registries. A's remove is held at `runningState`, and B's apply is started. B runs only after A releases the lock. At the end, the entry is in Claude's config, and B's item and record are intact.

## REJECT

- **l4 BLD-R2-06** (a retried nightly job may pick a newer heart nightly).
  - The per-job lookup is unchanged from `HEAD`, and `anytypeHelper` has always had this property.
  - heart's nightly tags are versioned, so within one job both macOS slices come from one tag (§4.5's "every architecture" holds).
  - Each package's forwarder and heart come from the same archive, and no state is shared across OS packages.
- **l1 P3-R2-09 / l4 BLD-R2-02, the revision half** ("check that both slices report the bundle's revision").
  - In the release flavour, both slices come from one `update-ci.sh` tag in one job: one heart commit, one `Rev`.
  - The non-host slice can't be run on every runner.
  - The namespace half is S10.
- **l1 P3-R2-03, "resolve the old intent before admitting the retry"**. Holding new mints behind recovery adds a cross-call state machine. S3's recheck in main covers both races with data main already has.
- **l2 SEC-02, "verify effective write or replacement rights"**. Computing effective rights is heavier and less certain than heart's own rule (allow entries only for the user, SYSTEM and Administrators), which S5 applies.
- **l1 P3-R2-05, "keep a manual installation pending until Check observes the entry"**. This goes beyond the lost-receipt bug: S7 alone restores the record's ownership of the entry, and how a manual setup reports before the user pastes the snippet is POC behaviour.
- **l4 BLD-R2-04, "carry the switch through packaged-bundle verification"**. With the switch on, `build-mcp.js` already fails a nightly without a signed bundle (`MCPB_SIGN_REQUIRED=1`), and `verify()` checks any bundle the metadata names.
- **l4 BLD-R2-03, "stage the dev forwarder per target"**. S14's verifier rule is enough, because main already refuses an arch without an entry.
- **l3 R2-08 / l4 BLD-R2-07, "inspect the effective DACL"**. S12 runs heart's own folder rule (`key set` / `key check`), which is the check that matters.
