# heart Phase 1 (`cmd/anytype-mcp`), review r1: adjudication

2026-11-27. Code: heart worktree `anytype-heart-mcp`, branch `go-0000-anytype-mcp` (5 commits on `origin/develop`). Review: four Codex lenses in `scratchpad/reviews/heart-p1-r1/`, cited as L1 (security, SEC), L2 (protocol, P), L3 (build/CI, BLD), L4 (Go quality, GO).

**Decision applied (Roma, 2026-11-27, final): no OS keychain on any OS.** One `0600` file per connection in a per-user Anytype folder, read and written only through the forwarder's verbs, with the same item and semantics (key, account, port, tier, rev; `fp@rev`; owner rule; per-connection lock; atomic write). Why: a keychain item only the forwarder can read gives it more rights than its caller, and anyone can run `serve --connection <id>` (a confused deputy). A file that the forwarder reads as its caller grants nothing extra. This replaces the same day's earlier per-OS decision (macOS ACL, Windows Credential Manager, Linux file). Port squatting and app binding stay follow-ups.

**Verification.** Every finding below was checked against the cited lines. `go vet ./cmd/anytype-mcp/...` is clean. `go test -count=1 -skip 'TestMacKeychain|TestRealStore' ./cmd/anytype-mcp/...` passes on macOS. `TestMacKeychain` was deliberately not run, because GO-03 shows it can write the login keychain. ## K1. One hardened file store on every OS (decision) — ACCEPT

This theme covers the decision, the file store's own findings (F1–F6 below, found while adjudicating), and four findings it settles. L1:SEC-08 and L3:BLD-02 become moot because no test build remains. L4:GO-03 and L3:BLD-04 are replaced by a scratch-folder guard. Today's test-build `File` (`internal/store/file.go`) becomes the production store, so it was checked as carefully as the backends:

- **F1 [high once shipped]: no safety checks.**
  - `os.ReadFile` follows symlinks and reads a FIFO (which blocks) or a file of any size (`file.go:43`). A FIFO at the item path hangs `serve` before its stdin reader starts (`serve.go:149`), the same class as GO-04.
  - `MkdirAll(0o700)` leaves an existing folder's mode alone (`file.go:54`), and nothing checks owner, mode or link count.
  - With a foreign-owned or group-writable folder, another OS user can plant an item (and so redirect the bearer) or read keys.
- **F2 [medium]: no `fsync`.** Neither the temp file nor the folder is synced (`file.go:57-69`). A power loss after the rename can leave an empty item, which reads as invalid, then absent, and the connection is lost silently.
- **F3 [medium]: errors other than ENOENT come back raw** (`file.go:43-47`).
  - The verbs report `store:"error"` with exit 1.
  - `serve`'s refresh treats them as final and ends the connection (`conn.go:148`). That contradicts §13: "a refresh that can't read the store keeps the last snapshot". This is L2:P10's rule, and it applies to any store.
- **F4 [low]: the `.state` fault hook** (`file.go:19-33`) must never ship, because a stray file would steer every verb.
- **F5 [low]: crash leftovers.** A crash between write and rename leaves `<id>.*.tmp`, which holds a whole item, key included, and is never removed.
- **F6 [medium, Windows]: a reader blocks the rename.** Go opens files with `FILE_SHARE_READ|FILE_SHARE_WRITE` only (`syscall/syscall_windows.go:395`). So a `serve` refresh or an antivirus scan holding `<id>.item` open makes the rename in `key set`/`retarget` fail.

**Fix.**
1. **Remove the backends.**
   - Files: `keychain_darwin.go`, `keychain_darwin_nocgo.go`, `wincred_windows.go`, `secretservice_linux.go` and its test, `real_test.go`, `keychain_darwin_test.go`, `testdata/linux-keyring.sh`, `other.go`.
   - Dependencies: `go mod tidy` drops `keybase/go-keychain`, `danieljoos/wincred` and `godbus/dbus` (checked: nothing else in heart imports them).
   - cgo: `keychain_darwin.go` is the only cgo file, so all five targets build with `CGO_ENABLED=0`. In `ci-cross-compile-mcp.mk`, drop the cgo flags from `MCP_DARWIN_ENV`; the darwin build no longer needs a macOS host.
   - API: drop `ServiceName`/`SecretServiceName` (replaced by a folder name), `ErrNoStore` and exit 4 (never returned), `--interactive`, `promptTimeout`, and the `locked` and `not-ready` reasons.
2. **Remove the test build.**
   - Delete the `teststore` tag, `open_teststore.go`, `overrides_*.go`, `TestBuild` and `"testBuild"`.
   - Tests point `HOME` (`USERPROFILE` on Windows) at a scratch folder. Instead of using `serve --port/--tier`, they write the item with the fake heart's port (`cli_test.go:601`, `integration_test.go:63,269,331`).
   - With only one build per namespace, the archive verifier keeps its existing namespace checks and needs no "refuse the test store" rule.
3. **Layout.** `store.Open(namespace)` uses the folder `<home>/.anytype/ai-connect/items` (release) or `…/items-dev` (dev).
   - The link-time namespace picks the folder name, and that name never changes.
   - Each item is `<id>.item`.
   - The lock moves to `<id>.lock` in the same folder, so every file the forwarder opens is inside one checked folder.
   - Home comes from `os.UserHomeDir()` and nothing else.
4. **Folder rule**, checked before anything else on every verb and every `serve` read.
   - **Unix:** `Lstat` `<home>/.anytype`, `…/ai-connect` and the items folder. Each must be a real directory (not a symlink), owned by the euid, with no group or other write bit. The items folder must be exactly `0700`. Create a missing folder with `Mkdir` and then `Chmod`, because of the umask.
   - **Windows:** no component may be a reparse point (`Lstat` reports `ModeSymlink` or `ModeIrregular`). Create the items folder with `CreateDirectory` and the descriptor `O:<user SID>D:P(A;OICI;FA;;;<user SID>)`. On every use, the owner and the DACL SDDL read with `GetSecurityInfo` must equal that string exactly.
5. **Item rule.** All access goes through an `os.Root` on the items folder, so nothing leaves it.
   - **Read:**
     - `root.Lstat` must report a regular file.
     - Open it, then `Fstat` the open file. It must be the same file, regular, owned by the euid, mode exactly `0600`, with one link. On Windows, the handle's owner and DACL must be `O:<SID>D:P(A;;FA;;;<SID>)`.
     - Read at most 4 KiB; anything longer is invalid.
   - **Windows readers** open with `FILE_SHARE_DELETE` (`windows.CreateFile`), so they never block a rename.
6. **Write**, under the lock:
   - Remove this id's stale `<id>.*.tmp` files.
   - Create `<id>.<rand>.tmp` with `O_CREATE|O_EXCL`: on Unix, `Fchmod 0600`; on Windows, `CreateFile` with the file descriptor above.
   - Write, `Sync`, `Close`.
   - `root.Rename` over `<id>.item`. On Windows, retry a sharing violation for up to 2 s.
   - On Unix, `fsync` the folder.
   - Any failure before the rename removes the temp file and returns a temporary error: exit 7, nothing written.
   - **Delete** is `root.Remove`.
7. **Error map.**
   - ENOENT is `ErrNotFound`.
   - A failed folder or item rule is temporary with reason `denied`, plus one stderr line naming the rule (never the key).
   - Every other error is temporary with reason `unreachable`.
   - `conn.refreshLocked` ends the connection only on `ErrNotFound`, `ErrInvalidItem`, another account or another tier. Anything else keeps the snapshot.
8. **Unchanged:** item format, `rev`, `fp@rev`, the owner rule and the lock. `--expect absent` still replaces an invalid item, which is now safe because the replacement is a new `0600` file.

**Tests.**
- **Store package**, on the macOS, Windows and Linux runners:
  - A round trip.
  - Created modes are `0700` and `0600`; on Windows, the SDDL matches exactly.
  - Each refusal returns `denied` and reads, writes and deletes nothing:
    - an item symlink, with its target inside or outside the folder;
    - a folder symlink or junction, and an ancestor symlink;
    - an item at `0644`, a folder at `0755`, a group-writable ancestor;
    - a hard-linked item (link count 2);
    - a FIFO or a directory at the item path;
    - a Windows DACL with an extra Everyone ACE;
    - a wrong owner, through an injectable euid (non-root CI can't `chown`).
  - A failed rename leaves the old item and no temp file.
  - A stale temp file is removed by the next write and never read.
  - With the folder at `chmod 000`: every verb exits 7, `serve` starts not connected, and a running `serve` keeps its snapshot.
  - On Windows, a reader holding the item open doesn't make `key set` fail.
- **CLI:**
  - The existing verb, concurrency and exit-code tests run the dev and release builds with a scratch `HOME`/`USERPROFILE` and no flags.
  - The `.state` cases become `chmod` cases.
  - Dev and release write to different folders.
  - Shipped builds refuse `--store-dir`, `--lock-dir`, `--port`, `--tier` and `--interactive` with exit 2.
- **Scratch guard (replaces GO-03/BLD-04).**
  - `TestMain` in `cmd/anytype-mcp` and in `integration` sets `HOME` and `USERPROFILE` to a fresh temp folder before any test runs.
  - The helper that runs binaries builds the child's environment from scratch, never from `os.Environ()`.
  - Store tests pass an explicit root.
  - A test that forgets one of these still can't reach the developer's home.
- **CI:**
  - Drop the gnome-keyring step and `ANYTYPE_MCP_REAL_STORE`.
  - Run `go test ./cmd/anytype-mcp/...` natively on all three OSes.
  - Lower `maxNonStdDeps` (`guard_test.go:27`).

## K2. The reset warning is written before any later tool call runs — ACCEPT (L2:P01, L4:GO-01, L1:SEC-07)

**Failing scenario.** After a curated-tier renewal, the writer clears `resetPending` and takes the sequence cut in `r.before()`, before `Out.Write` (`serve.go:482-493`, `235-239`). While stdout is blocked on the warning line, a `tools/call` read after the cut passes `resetBlocks`, and its write runs in the new session before the client has seen the warning. There is a second window: `handle` checks the gate (`serve.go:512`) and reads the session separately (`serve.go:523`), so a renewal between the two lets a call that passed the old gate run on the new session.

**Simplest safe fix.**
- Take the cut in an `after` hook, once `Out.Write` has returned without error.
  - The cost: a call that the client sends within microseconds of reading the warning may get the warning again. That warning says "This call did not run", so this is safe.
- Add one locked step, `admit(seq) (session, version, blocked)`, which reads the gate and the session together.
  - A `tools/call` uses that session for its whole life; the retry loop no longer re-reads it.
  - A renewal after admission makes heart answer 404 for the old id, and the call ends with the warning through `renew`'s `current != stale` path.

**Regression tests.**
- A stdout writer that blocks on the warning line, and a `tools/call` sent after the warning is queued. The fake heart receives no `tools/call` until that write returns.
- A hook that pauses a worker after admission while a renewal completes. That call never reaches heart with the new session id.

## K3. Shutdown: a fixed 10 s deadline with hard stops; the logger never blocks — ACCEPT (L2:P02, L4:GO-06, L4:GO-05, L1:SEC-09)

**Failing scenarios.**
1. On EOF with stdout stalled and 32 replies queued, `flush`'s `s.send(marker)` (`serve.go:211-213`) can't see the deadline. Exit waits for the 30 s stall watchdog.
2. If stdout breaks during the EOF flush, `flush` returns but the code stays 0 (`serve.go:175-176`), so replies are lost while the process reports success.
3. On SIGTERM or a broken stdout, with the host not draining stderr, `log.printf` blocks before `stopRun` (`serve.go:185,188`; `log.go:23-25`) and the process never exits. Every worker that logs blocks the same way.
4. SEC-09: the logger strips only `\n`, so a client-chosen `method` reaches stderr with every other control character intact.

**Simplest safe fix.** One rule: from the trigger, `Serve` returns by the deadline whatever is still blocked, and `main`'s `os.Exit` ends the stuck goroutines.
- `flush` selects on the deadline and on `broken`, for both the enqueue and the wait, and reports whether the marker was written. If it wasn't, the exit code is 1.
- The logger never blocks.
  - `printf` puts the line into a buffered channel of 64 lines, drained by one goroutine. When the channel is full, the line is dropped and counted.
  - At shutdown, the drain gets whatever time is left of the deadline.
  - Every control character is replaced (`unicode.IsControl`), and a line is capped at 512 bytes.

**Regression tests.**
- EOF, a stdout that never accepts, and 32 queued replies: `Serve` returns within the deadline plus slack, with exit 1.
- SIGTERM with a stderr that never accepts: `Serve` returns within the deadline, and the `DELETE` reached the fake heart.
- A method containing `\r` and ESC is logged without them.

## K4. Each session is owned by the snapshot that opened it — ACCEPT (L1:SEC-04, L2:P06, L4:GO-08, L2:P07, L2:P08)

**Failing scenarios.**
- **SEC-04: a stale port at shutdown.** An idle curated client opened its session on port A, and Anytype has since restarted on port B. Hours later the client exits, and `endSession` sends the bearer to A (`serve.go:821-833`). Another program may now hold A, possibly another OS user's. This breaks the 5 s window in §2.4.
- **P06/GO-08: renewal overwrites a client initialize.** While a renewal waits for `notifications/initialized`, a client `initialize` installs session X. The renewal then overwrites it with Y unconditionally (`serve.go:804-808`).
  - X leaks against heart's limit of 8 sessions per key.
  - The client's next call goes to Y, which was opened with the old params.
- **P07: lost and unbounded cleanup.** Failed or replaced sessions are dropped in fire-and-forget goroutines that use `runCtx` (`serve.go:622,720,774,815`).
  - EOF cancels them before the `DELETE` is sent.
  - They run outside the 4-worker bound, and heart refuses the 9th call per key.
- **P08: renewal checks too little.**
  - `renew` ignores its reply's id and `isJSON`.
  - It accepts any status below 300 for the notification (`serve.go:790-803`).
  - A 401 on either leg becomes "try again" instead of `-32001`.

**Simplest safe fix.**
1. `s.session` becomes `{id, version, snap}`, where `snap` is the snapshot that opened it.
2. `renew` commits only if `s.session.id` is still `stale`, checked under `s.mu`. Otherwise it hands Y to cleanup.
3. Cleanup is one goroutine fed by a channel.
   - It sends each `DELETE` with the session's own snapshot, one at a time, with a 5 s timeout on `context.Background()`, so at most 5 calls are in flight, under heart's 8.
   - Shutdown closes the channel, waits for it within the deadline, then handles the current session.
4. The shutdown `DELETE` first calls `s.conn.current(deadline)`, which re-reads the item if the last read is older than 5 s.
   - It is sent only if that succeeds and the port and key still equal the session's snapshot.
   - Otherwise it is skipped, and heart's 30-minute idle timeout ends the session.
5. Renewal validates its reply like any other.
   - The reply must be JSON and carry the renewal's generated id.
   - The notification must be answered with 202.
   - A 401 on either leg triggers a refresh and maps to `-32001` with the "key rejected" text.

**Regression tests.**
- Retarget the item to port B after `initialize`, move the clock past 5 s, send EOF: the fake heart on port A receives no `DELETE`.
- Hold the renewal's notification reply until a client `initialize` succeeds: the next call uses X, and Y gets a `DELETE`.
- A failed `initialize` that returns a session id, followed at once by EOF: the `DELETE` arrives before exit.
- A 401 on either renewal leg gives `-32001`; a 200 JSON-RPC error answering the notification fails the renewal.

## K5. Never reply to a cancelled request — ACCEPT (L2:P03, L4:GO-07)

**Failing scenario.** A worker finishes its exchange and blocks in `s.send` because the reply queue is full (`serve.go:436-441`, `200-209`). The reader then handles `notifications/cancelled`, but the reply is still written. Also, the deferred `release` drops the call from `live` once its reply is queued (`serve.go:383-393`), so a cancel for an already queued reply is ignored.

**Simplest safe fix.** Rule: a reply is written only if its request wasn't cancelled before the writer committed to that reply.
- Each reply carries its `call`, and the call stays in `live` until the writer takes the reply.
- The writer, under `s.mu`, drops the reply of a cancelled call. Otherwise it marks the call committed and removes it from `live`.
- `cancelRequest`, under `s.mu`, ignores a committed call.
- `s.send` also selects on `c.ctx.Done()`, so a blocked enqueue gives up when its request is cancelled.

**Regression tests.**
- With stdout blocked, cancel a request whose worker is blocked on the enqueue: no reply is written.
- Cancel a request whose reply is already queued: no reply is written.
- A cancel that arrives after the line was written has no effect.

## K6. The bearer is never relayed in a 200 reply — ACCEPT (L1:SEC-05)

**Failing scenario.** Heart sends tool failures as HTTP 200 with `result.isError` (`core/api/wrapper/mcp.go:496`). `relay` re-encodes a 200 error or result verbatim (`serve.go:634-655`); only the 400 and 5xx paths go through `redact`. If heart ever echoes the bearer, through a bug or an object the user pasted the key into, the key lands in the AI transcript, which the vendor may store in its cloud.

**Simplest safe fix.** Before relaying any 200 body, check `bytes.Contains` for the key and for its JSON-escaped form (`json.Marshal(key)` without the quotes; it differs only for keys containing `"`, `\`, `<`, `>` or `&`). On a hit, reply under the request's id with a fixed text, "Anytype's reply contained this connection's key and was withheld" (`isError` for `tools/call`, `-32603` for anything else), and log one line.

**Regression test.** Put the canary key in result text, in `error.message`, in `error.data`, and in HTML-escaped form. The reply is withheld every time, and the canary never reaches stdout.

## K7. Exit 7 means nothing was written; one complete payload — ACCEPT, part (L4:GO-09, L1:SEC-10, L4:GO-15)

**Failing scenarios.**
- **GO-09.** The write succeeds and the read-back fails (`commit`, `key.go:278-283`). The verb exits 7, "try again", which §2.8 defines as "nothing changed", so the desktop may revoke the new key that the item now holds. With the file store this happens when the rename is done and the folder `fsync` or the read-back fails.
- **SEC-10/GO-15.**
  - `readPayload` reads through `LimitReader` (`key.go:256`), so a line cut at 16 KiB looks like EOF.
  - One `Decode` accepts a valid object followed by garbage. `DecodeItem` does the same (`item.go:86-90`).

**Simplest safe fix.**
- Exit 7 always means nothing was written.
  - A failure after the store took the write (the rename returned) is exit 1 with `{"ok":false,"unconfirmed":true,…}`.
  - §13 tells the desktop to treat `unconfirmed` as a lost receipt: reconcile with `key check` (§2.9) before releasing or revoking anything.
- Input:
  - Read `maxPayload+1` bytes; anything longer is exit 6, decided before the lock is taken.
  - After `Decode`, the next `dec.Token()` must return `io.EOF`.
  - `DecodeItem` applies the same rule.

**Rejected part.** Exact-case or duplicate member names (SEC-10). The payload and the item each have one producer and one reader, the same Go decoder, so there is no second interpreter to disagree with.

**Regression tests.**
- A store double whose read-back fails after a successful write: exit 1 `unconfirmed`, and the item holds the new key.
- A payload followed by `x`, and a 16 KiB + 1 line: exit 6, nothing written.
- A stored item followed by garbage counts as invalid.

## K8. Correlate and cancel by the decoded string id — ACCEPT, part (L2:P04, L4:GO-10)

**Failing scenario.** Heart echoes the id as a `json.RawMessage` through gin's `c.JSON` (`core/api/server/mcp.go:433`), which escapes HTML characters. A request with id `"a&b"` gets its reply as `"a&b"`. `relay` compares raw bytes (`serve.go:630`), so a write that ran is reported as "outcome unconfirmed". A cancel that spells the id with a different escape misses the `live` map (`serve.go:406`).

**Simplest safe fix.** Add one function, `idKey(raw)`: a JSON string maps to `"s:"` plus its decoded value; a number maps to `"n:"` plus its raw bytes, so precision is kept. Use it in `relay`'s comparison and for the `live` map. The client still gets back its own raw id.

**Rejected part.** Accepting `"jsonrpc":"2.0"`: no client sends it, and refusing it is safe.

**Regression tests.**
- A real-heart call with id `"a&b<c>"` is relayed as a result.
- A cancel naming `"a&b"` cancels the request `"a&b"`.

## K9. The stdout stall timer measures progress — ACCEPT (L2:P05, L4:GO-11)

**Failing scenario.** `writeBegan` is set once for a whole line (`serve.go:238-240`). A 100 MiB reply that the client drains steadily for more than 30 s counts as stalled, so the line is cut and the process exits 1.

**Simplest safe fix.** The writer writes each line in 64 KiB pieces and records the time after each piece. The watchdog measures from the last piece. There is still one writer, so lines never interleave.

**Regression test.** A reader that accepts 64 KiB every `StdoutStall/2`, for three times `StdoutStall`, receives the whole line, and the process doesn't exit.

## K10. The rev guard covers dependencies; regenerating the lock requires a bump — ACCEPT, part (L3:BLD-01, L4:GO-12, L4:GO-13)

**Failing scenarios.**
- **BLD-01/GO-12.**
  - The hash covers only `.go` sources (`guard_test.go:64-90`), so a dependency bump changes the binary at the same `Rev`.
  - `UPDATE_REV_LOCK=1` rewrites `rev.lock` with the old `Rev` (`guard_test.go:100-102`), so a source change also passes without a bump.
- **GO-13.**
  - The dependency budget sets only `GOOS` (`guard_test.go:38-42`).
  - `HasPrefix(pkg, ownPrefix)` also matches a sibling package such as `…/anytype-mcpX`.

**Simplest safe fix.**
- Also hash `go list -deps -f '{{with .Module}}{{.Path}}@{{.Version}}{{end}}'` across the five shipped targets, deduplicated and sorted.
- `UPDATE_REV_LOCK` refuses to write unless `Rev` is greater than the `Rev` in the current lock.
- The budget iterates the five `GOOS`/`GOARCH` pairs with `CGO_ENABLED=0` (after K1) and matches `pkg == ownPrefix || HasPrefix(pkg, ownPrefix+"/")`.

**Rejected part.** Pinning the exact Go patch in CI and hashing it. That is a heart-wide CI change. Two builds of the same sources at the same `Rev` are interchangeable, and a security-relevant Go fix gets a manual bump, as §1.2 already says.

**Regression tests.**
- A changed module version in the hashed list changes the hash.
- `UPDATE_REV_LOCK` with an unchanged `Rev` fails.

## K11. Small fixes — ACCEPT, part (L2:P09, L2:P12, L3:BLD-07)

- **P09.**
  - **Failing scenario:** `forwardQuiet` only logs a refused connection (`serve.go:451-454`), so a notification sent just after a port move is lost.
  - **Fix:** on `outRefused`, refresh and retry once. Nothing was sent, which §2.4 already allows for requests.
  - **Rejected part:** renewing on a notification's 404, because the next request renews anyway.
  - **Tests:** the forwarding test asserts that heart received the client response as well as the notification. A refused first port leads to delivery on the new port.
- **P12.**
  - **Failing scenario:** the retarget subtest writes the port and tier the child already uses (`integration_test.go:326-334`), so a child that never re-reads still passes.
  - **Fix:** start the child on an item that names a loopback relay to heart. Retarget the item to heart's own port, close the relay, and require that the same child's next `tools/list` succeeds.
- **BLD-07.**
  - **Failing scenario:** `-tags integration` doesn't compile on Windows, because `heartboot` uses `Setpgid` and `syscall.Kill`.
  - **Fix:** use `//go:build integration && !windows` and say so in `doc.go`.

## K12. Plan text — ACCEPT

Plan file: `anytype-mcp-plan.md`. Add a dated line at the top: "2026-11-27: no OS keychain on any OS (Roma)".

- **§0.1**
  - Delete D2.
  - D5 becomes "One `0600` file per connection".
  - N1 becomes "One file holds key + account + port + tier + rev. No locator file".
- **§0.2** (replace)
  - **In scope:**
    - The key at rest is one file per connection: mode `0600`, in a `0700` folder owned by the user (on Windows, an owner and DACL limited to the user). It is read and written only through the forwarder's verbs. Other OS users can't read, plant or replace it.
    - No key in argv, the environment, logs, AI-app configs, or any file except its own item.
    - No use of one account's key under another account. No lost revocations. The bearer goes only to `127.0.0.1`.
  - **Out of scope (one residual):**
