Verified while adjudicating (read-only; no repository file touched):
- `check()` (index.ts, the `keys !== null` block): every candidate the key list marks absent leaves `unconfirmed`, and its hash goes to `revokePending`. This happens before `settleUnconfirmed` reads the item. The staged baseline only dropped such a candidate. heart's `list()` skips grant files it can't read (`core/wallet/applink.go`, `continue // Skip files we can't read`).
- `exec.ts runFile`: `close` with a signal (`code === null`) and the MAX_BUFFER kill both give `code: -1`. `keyStore.writeOutcome` maps every non-timeout `-1` to `verify/notFound` ("nothing ran").
- `apply`'s `journal.set` saves the candidate with `running: false` while `key set` runs.
- `'done' in (await deleteItem(…))` is true for `{ done: false, left: true }` too. `revoked()` deletes a removed record as soon as `revokePending` is empty, whatever `itemDelete` says. `removedRecord()` drops `unconfirmed`, so a retry knows only `keyFp`.
- `claudeDesktop.remove`: `deleteItem` answers `done` for a foreign item, and the config entry is then removed when `entryOurs` matches. Both accounts write the identical `serve --connection claude-desktop` entry, so its digest always matches.
- `withLock`: any create error reads the lock. `Number(null) === 0` makes the lock stale, so the code unlinks it and runs `continue` without a sleep or a deadline check: a synchronous loop on main.
- Mint intents:
  - `apply` calls `dropIntent` before `saveCommitted`;
  - `recordManual` calls it whatever `saveCommitted` returned;
  - `createApp` folds dispatcher transport errors and empty replies into `ok: false`, and the renderer then clears the intent;
  - `addIntent` evicts the oldest intent at `MAX_INTENTS`.
- `extensionInfo` returns `outdated` before it reads `isEnabled`. `manualPrepare`'s config branch has no enabled-extension guard.
- BLD-01 reproduced on this Mac. `set -o pipefail; codesign -d --verbose=4 /Applications/Anytype.app/Contents/MacOS/Anytype 2>&1 | grep -qx 'Identifier=com.anytype.anytype'` gave 141 in 3 of 3 runs (1088 bytes of output).
- Workflows:
  - Linux packaging is a bare `electron-builder --linux` on `ubuntu-22.04`, the same as before Phase 3, and `build.linux.target` names no arch: x64 only.
  - `build.yml` runs on `v*` tags only.
  - `asarUnpack` has no `electron/json` entry.
- `prepare-forwarder.js` on Linux:
  - `linux-amd/` and `linux-arm/` take precedence over `dist/anytype-mcp`, so an `ANYTYPE_MCP_BIN` copy is ignored when they exist;
  - the release marker alone sets `signed = true`;
  - `beforebuild.js` copies `linux-*/anytype-mcp` over `dist/` at packaging time as well.
- `sign.js` interpolates `AZURE_CLIENT_SECRET` into a shell command. `Util.execPromise` logs the whole `exec` error, and an exec error's message contains the command line. `prepare-forwarder.js` rethrows `e.message`.

## High

Q1 **A key list never retires a candidate; only `key check` settles it** (l1 P3-02, l2 SEC-02, l3 R03).
- Scenario: a rotation from A to B writes B into the item, then loses its receipt. The next ListApps succeeds but omits B (an unreadable grant file). `check` queues B for revocation and drops it from the candidates before `settleUnconfirmed` runs. The renderer revokes B in the same pass. The client's key is dead, the record keeps A, and the user sees "conflict". This contradicts §2.9 ("a key list that merely lacks the hash proves nothing") and §8.2.
- Fix (index.ts `check`): delete the list-based candidate filter (`candidates` / `dropped`) for every adapter. A candidate leaves `unconfirmed` only through `settleUnconfirmed`, which reads its own target. That function already keeps everything while a target is `unreadable` or a writer may still run, and queues only the loser. A promoted key that heart doesn't list reports `accessEnded` through the existing status rule. Update the §13.2 line "A candidate the list lacks leaves the candidates but its hash is queued".
- Tests ("Q1: …"):
  - From A to B with a lost receipt and the item holding B, the key list says B `present: false`. The check promotes B and queues only A. In the renderer pass, RevokeApp is called for A and never for B.
  - The same with the store `unreachable`: the record keeps A plus candidate B, and nothing is queued.
  - Fix the POC tests that relied on the drop by settling them through the target instead.

Q2 **A killed or signalled key writer is unconfirmed, never "not started"** (l1 P3-03, l2 SEC-11, l3 R02).
- Scenario: `key set` replaces the item, then dies by signal (or the MAX_BUFFER kill) before printing its receipt. `runFile` returns `code: -1`, and `writeOutcome` calls it `notFound`. The service removes the candidate, the popup releases B on close, and the installed key is revoked.
- Fix:
  - `runFile` records whether the child spawned (the `'spawn'` event) and marks a failure to start explicitly: the synchronous throw, or `'error'` before `'spawn'`, gives `notStarted: true`.
  - `writeOutcome` returns `notFound` only for `notStarted`. Every other `-1` after a spawn is `unconfirmed`, and so is a timeout.
  - A timeout whose end couldn't be confirmed (`indeterminate`) also sets `running: true` on the outcome, so the candidate is saved as running (U2).
- Tests ("Q2: …"):
  - `keyStore.test.ts`: the stub records the call, then `process.kill(process.pid, 'SIGKILL')`, giving `{ unconfirmed: true }`. A missing binary gives `notFound`.
  - Service: the fake forwarder writes the item, then answers `{ code: -1, stdout: '' }` (spawned). Apply is unconfirmed, the candidate stays, the next check promotes it, and zero RevokeApp reaches the installed key.

Q3 **A journaled key write counts as in flight until its deadline** (l1 P3-04).
- Scenario: Electron exits while `key set` waits for the item lock, and the helper survives. A quick restart's check reads the old fingerprint and retires B as finished (`running: false`), and the renderer revokes it. The helper then installs the revoked B. This breaks U2 ("nothing is settled while a delivery may still be running").
- Fix:
  - `journal.set` saves the candidate with `running: true, until: now + keyStoreConfig.timeout + 5 s`. heart ends every verb within 30 s (§13).
  - The verb's own result replaces that candidate as today: commit, removal, or an unconfirmed candidate.
  - `settleUnconfirmed`, and the `waiting` test after it, treat a candidate as running while `running && (!until || now < until)`. A matching fingerprint still promotes it at once.
  - `isCandidate` accepts the optional `until`.
- Test ("Q3: …"): snapshot the registry at the moment the fake forwarder receives `key set`, and restart the service from it with the item still holding A.
  - A check inside the deadline: B stays a candidate, and nothing is queued.
  - The fake then writes B: the next check promotes B and queues A.
  - Past the deadline with the item still holding A: B is retired.

Q4 **Item-deletion records are cleared only by a confirmed `key delete` / `key check`** (l1 P3-05, l2 SEC-06, l3 R05).
- Scenario: Disconnect runs while the store is unreachable (`itemDelete` stays set). The renderer revokes every hash, and `aiConnectRevoked` deletes the record. The item, holding a dead bearer, stays on disk with nothing left to retry. Separately, the check's retry tests `'done' in result` and clears `itemDelete` on `{ done: false, left: true }`. After a lost rotation receipt, a removed record no longer knows the candidate fingerprint in the item, so it calls the item foreign and leaves it.
- Fix:
  - `check`: `if (rec.removed && rec.itemDelete && (await deleteItem(…)).done === true)`.
  - `revoked()` and `check` delete a removed record only when `!revokePending.length && !itemDelete`. While only the item is pending, `check` sets the status `removed` (not `revokeFailed`), so the row stays hidden.
  - `removedRecord()` keeps `itemFps` (the record's `keyFp` plus every candidate fingerprint) while `itemDelete` is set, and `ownFps` includes them.
  - `deleteItem` re-reads once after `precondition` (two attempts, like `commitItem`) before it answers `done`.
- Tests ("Q4: …"):
  - Disconnect with the fake store `unreachable`. In the renderer's startup order (revoke, `aiConnectRevoked`, then check), the record survives with `itemDelete`. With the store back, the next check deletes the item and only then removes the record.
  - The same after a lost rotation receipt with B in the item: B's item is deleted.
  - `{ done: false, left: true }` keeps `itemDelete`.

Q5 **Claude config ownership is keyed by account; disconnecting A never touches an entry owned by B** (l1 P3-01, l2 SEC-07, l3 R04).
- Scenario: A connects Claude through the config route. B replaces it with consent. A disconnects while Claude is stopped. `deleteItem` answers `done` for B's item, the identical entry matches A's digest, and `mcpServers.anytype` is removed. B's item survives, but Claude never starts the forwarder again.
- Fix:
  - `deleteItem` returns `{ done: true, owner: 'deleted' | 'none' | 'foreign' } | { done: false, left: true }`.
  - `claudeDesktop.remove` (also reached through `removePrevious`) removes the config entry only for `deleted` or `none`.
  - `foreign` leaves the entry alone and reports nothing, because the entry is B's now.
  - `left` keeps the entry and reports `left: 'entry'`.
  - A's hashes are revoked in every case.
- Test ("Q5: …"): connect A, connect B with Replace, then disconnect A with Claude stopped. Claude's config is byte-identical, B's item and record are intact, and A's hashes are queued. With the store unreachable, the entry stays and `left: 'entry'` is reported.

Q6 **A mint intent is cleared only once its key is durably accounted for; an ambiguous CreateApp keeps it** (l1 P3-08, l2 SEC-04, l2 SEC-05 (dropped-reply and limit parts), l3 R10).
- Scenario:
  - A file/CLI delivery commits, then main dies between `dropIntent` and `saveCommitted`, or both save attempts fail. A live key then has neither a record nor an intent.
  - `recordManual` drops the intent even when the record exists only in memory.
  - A CreateApp whose reply is lost (dispatcher transport error, empty response) clears the intent although heart may have minted the key.
  - The 65th intent silently evicts the oldest unresolved one.
- Fix:
  - main: `apply` (both the committed and the unconfirmed branch) and `recordManual` call `dropIntent` only when `saveCommitted` returned `true`. A pending in-memory save keeps the intent. The next run then finds the key managed (and clears the intent) or orphans it.
  - renderer: `mintKey` (including the `late` branch) never clears the intent on a failed CreateApp. Only a committed delivery or a confirmed release clears it, and the next run's check clears an intent that matches no key.
  - `Registry.addIntent` refuses (throws) at `MAX_INTENTS` instead of evicting. `mintKey` then answers `write/unsaved`, and no CreateApp is sent.
  - Update the §13.2 line "cleared by … a refused CreateApp".
- Tests ("Q6: …"):
  - Service: apply and recordManual with every registry write failing twice. The intent is still in the registry file, and a restarted service reports it in `mintIntents`.
  - Renderer: CreateApp answers a transport error. No `aiConnectMintIntent { done: true }` is sent.
  - With 64 live intents, `mintKey` makes no CreateApp call.

Q7 **Stable-copy lock acquisition is async with a timeout and never blocks the main process** (l1 P3-07, l2 SEC-09, l3 R01).
- Scenario: `~/.anytype/bin` is read-only, the disk is full, or `.lock` is a directory. Every exclusive create fails, the empty or missing lock reads as time 0, and `withLock` unlinks it and continues without a sleep or a deadline check. Electron's main process freezes on Connect or on a background check.
- Fix (forwarder.ts `withLock`):
  - Only `EEXIST` is contention; any other create error returns `null` (`installFailed`) at once.
  - Staleness comes from the lock's `lstat` mtime (> 60 s), not its content, so an empty lock that another installer is still writing is never stolen.
  - A failed stale unlink counts as contention.
  - Every retry path sleeps 200 ms and checks the 10 s deadline.
- Test ("Q7: …"), with a fake clock:
  - `writeFile` throws `EROFS`: `ensureInstalled` returns `installFailed` with zero sleeps.
  - A `.lock` directory older than 60 s: `installFailed` after the deadline, with sleeps in between and a bounded number of attempts.
  - A fresh, empty `.lock` file is not removed.

Q8 **The namespace is chosen by the build flavour (signed release CI only), never by a reused checkout's leftovers** (l1 P3-09, l2 SEC-10, l3 R07, l4 BLD-04, l4 BLD-08).

  - The `ci` "no forwarder" error applies to the release flavour only.
  - `beforebuild.js` copies `linux-*/anytype-mcp` only in the release flavour.
  - `update.sh` removes `$folder/anytype-mcp$mcp_ext` in the branch where the archive has no dev member.
- Tests ("Q8: …") with `prepare()` fixtures:
  - dev flavour, release leftovers in `linux-amd`, `ANYTYPE_MCP_BIN` dev: that binary is used with `signed: false` and namespace `dev`;
  - dev flavour with only release leftovers (Linux and macOS): `null`, never `signed: true`;

Q18 **The stable copy is used only when another OS user can't replace it, and only when it can execute** (l2 SEC-01 (POSIX half), l1 P3-14, l3 R13).
- Scenario:
  - A `~/.anytype` that its group (or others) may write lets another user swap `bin` for their own folder. The AI app then runs their binary as the victim, with every item readable. `ownDir(.anytype, false)` checks only the owner.
  - Separately, a restored copy with the right bytes but mode `0644` passes the hash-only `same()`, and every client fails to launch it.
- Fix (forwarder.ts `ensureInstalled`):
  - (a) `.anytype` must be owned by the user and not writable by group or others. This is heart's §3 Unix rule, and it is never chmod-ed because the folder is shared with heart. Otherwise the result is `installFailed`, so no command is handed out, and a check reports `reconnect`.
  - (b) On POSIX, a copy counts as usable only with owner = user and mode exactly `0755`, both on the equal-hash path and on the higher-rev keep path. A wrong mode is repaired with `chmod 0755` under the lock, or the result is `installFailed`.
- Test ("Q18: …"):
  - `.anytype` at `0775`: `installFailed`, nothing written, no key verb.
  - An equal-hash copy at `0644`: chmod-ed to `0755`, then ok.
  - The same for a higher-rev copy.
