# Claude Replace fixes (854681ee65) and Azure bundle signing (01f6512a57), final capped review: adjudication (orchestrator)

Raw: scratchpad `reviews/rep-r2/out1.md` (the fix-round commit) and `out2.md` (signing), both gpt-6.2-astra xhigh, critical/high only. This is the last round. After these fixes the change is accepted without another full round. The orchestrator checks the fixes against the tests.

## ACCEPT: main process (lens 1)

F1 (R17a) **The installed extension matches our manifest exactly.** Before offering Configure or marking it ours, compare the installed `manifest.json`'s `server` (including `mcp_config` and any `platform_overrides`) and `user_config` with the manifest of the bundle this build ships. Any difference → not ours (outdated).

F2 (R5) **Check the process first, then re-check the file right before the rename.** In `writeFileSafe`, run `beforeRename` (the async process lookup) first. Then, synchronously and immediately before every rename attempt, re-check the directory and the snapshot. An edit made during the lookup must survive: abort and revert.

F3 (R3) **Pin the canonical target.** The locked checks compare the resolved real path with the one agreed at staging on every read, including the "entry absent" branch. If the path differs, refuse and undo.

F4 (R1b) **Make the config change durable before the revoke is committed.** After the rename that removes the entry, fsync the containing directory (POSIX; best effort on Windows) before the registry commit that queues the old key.

F5 (R1c) **A failed bundle copy stops before anything is changed.** If `copyBundle` fails, return its error before staging, quitting Claude or editing its settings.

F6 (R2a) **An unresolved recovery never exposes a staged record.** While a staged record can't be recovered, `aiConnectList` shows the last committed record, and the key-copy and Open-again paths refuse the staged one.

F7 (R2b) **A restored mint intent keeps the exact hash.** When a refused replacement restores the mint intent, persist the known `appHash` on it, and have recovery use the exact hash, so the key is revoked even when name, grant, expiry and time window are ambiguous.

## ACCEPT: signing and workflows (lens 2)

F8 (H3) **DER-canonical signed attributes.** Order the authenticated attributes so the encoded SET OF is sorted: contentType, signingTime, messageDigest. Do this in both passes. Test with a verifier that re-encodes the attributes (e.g. OpenSSL `cms -verify`, or a re-encode-and-compare check). We deliberately differ from `mcpb sign` here (it has the same flaw); our check of the signature must still pass.

F9 (H4) **Azure credentials only in a dedicated signing step.** "Build frontend" (`bun run build`, Vite and its plugins, the forwarder's `version --json` probe) runs without any `AZURE_*` value. It builds the unsigned bundle and its metadata. A separate step with only the Azure values signs `dist/mcp/Anytype.mcpb`, verifies it, and rewrites `mcpb.sha256` / `signed` / `signerFingerprint` in `electron/json/aiConnect.build.json` before packaging. Do the same in nightly.yml behind its switch. The Windows forwarder signing that needs AzureSignTool stays where it must run, but with the fewest steps possible holding the values.

F10 (H5) **No Azure values on Linux.** Guard the five Azure entries of "Package and publish Other" with `startsWith(matrix.os, 'windows-')` in both workflows.

## REJECT / RESIDUAL

- R17b (identity re-check between the check and the key copy at Configure): an attacker who can rewrite files in the user's Claude extension directory already runs as the user. That's outside the threat model (tokens-plan §2).
- R1a (the second registry save fails after the config rename, so the old record comes back without its entry): rare (storage failing between two writes). Nothing is orphaned: the old key stays tracked by its record, which shows "Removed in Claude", and Disconnect or Reconnect resolves it. Residual.
- H2 (require Claude's own verifier to say "signed"): Claude Desktop's current verifier can never say "signed" (forge `p7.verify` is unimplemented), so this would block every release. We sign for verifiers that work, and identify our extension by its files (R17).
- H1 (middleware pin lacks `anytype-mcp-release`): a release-order issue, not a code defect. The desktop PR merges only after heart #3353 is merged, a heart version with the forwarder exists, and `middleware.version` is bumped in this PR.
