# Phase 5 (follow-ups after Roma's review) code review, round 1: adjudication (orchestrator)

Raw: scratchpad `reviews/p5-r1/lens1.md` (correctness, P5-xx), `lens2.md` (security, SEC-xx), `lens3.md` (robustness, P5-xx), `lens4.md` (UX/spec, UX-xx). The reviewers were briefed with `reviews/p5-extra.txt`. Ids overlap across files, so findings are cited as file+id (for example l1 P5-01, l3 P5-01). Of about 60 findings, 21 themes plus HX are accepted below, 3 findings are rejected, and one structural fix is replaced by a copy change. Every fix gets a regression test on the production path (the service with the fake home for main, and the popup/controller boundary for the renderer). Tests are named "H<n>: …". Use the simplest safe fix. For Hermes files the rule is: **if anything looks unusual, refuse and give manual steps**. Do not add clever handling.

Verified by the orchestrator while adjudicating:
- `yaml` 2.3.1 rewrites `1234567890123456789` as `1234567890123456800`, `0x1F` as `0x1f` and `1e3` as `1e+3`, and the parsed-value check accepts all three. An inline `<<: { anytype: … }` parses as an ordinary key with no warning. GHSA-48c2-rrv3-qjmp (stack overflow on deeply nested collections) affects `yaml` below 2.8.3.
- Hermes writes `config.yaml` with PyYAML `yaml.dump(default_flow_style=False, sort_keys=False)` (`utils.atomic_yaml_write`), which produces indentless lists (`key:\n- a`). The current writer (`{ lineWidth: 0 }`) re-indents every list in such a file, which changes text outside our entry. A PyYAML-style sample round-trips byte for byte with `{ indentSeq: false }` and the default line width, including folded long strings and Hermes' trailing comment sections.
- `writeFileSafe` copies the whole previous file to `<file>.anytype-backup`. For `.env` that copy holds every provider credential.
- The anytype-hermes docs (INSTALL.md) use a fixed `/tmp/anytype-cli-install.sh`, always pass `--input anytype-setup.json` (`credential_backend: private_file`) on the fresh-bot path, and recommend a named profile (`hermes profile create anytype --no-alias`, then `-p anytype` throughout). The README says: "Allowlists … do not isolate its MCP tools".

## High: Hermes credentials and files

H1 **The YAML edit is lossless, or it is refused** (l1 P5-01, l3 P5-01, SEC-08, SEC-12). Connecting Hermes silently changes a 19-digit Discord/Telegram ID elsewhere in `config.yaml`, and it also re-indents every PyYAML list. Fix in `yamlFile.ts`:
- (a) Wrap `parseDocument` in try/catch so that a throw becomes `unparseable`. Bump the direct `yaml` dependency to ^2.8.3 and update the lockfile.
- (b) Refuse with `unsupportedForm` when the document has any anchor, alias or `<<` merge key anywhere. Check this with `visit` on the Document.
- (c) Make a no-op re-serialization the guard. Before editing, `parse(text).toString(OUTPUT)` must equal `text` byte for byte; otherwise refuse with `unsupportedForm`. Untouched nodes then serialize identically, so the only text change is our entry. Keep the existing parsed-value check as a second guard.
- (d) Set `OUTPUT = { indentSeq: false }` with the default line width, so Hermes-written files pass.
- Optional: also accept a file that round-trips with `indentSeq: true` (hand-indented lists), and edit it with the options that matched.
- Apply the same guard to `removeYamlPath`.

Tests:
- A 19-digit ID, `0x1F` and `1e3`: the plan is manual and the file is byte-identical after apply.
- An inline `<<` merge that supplies `anytype` is refused and not classified as absent.
- A Hermes-written fixture (indentless lists, a folded long string, the `# ── Security ──` trailer) still auto-applies, and the text diff is exactly the inserted entry lines.
- A deeply nested document returns `unparseable` and does not throw from `check`.

H2 **`.env` comes from the profile directory, not from the resolved `config.yaml`** (l1 P5-02, SEC-04, l3 P5-04, UX-03, plus the second half of l1 P5-03). If `~/.hermes/config.yaml` is a symlink into `~/dotfiles`, the key is written to `~/dotfiles/.env`, which Hermes never reads. Fix:
- `envFileOf` becomes `join(hermesHome(env), '.env')`: the default profile, unresolved. Use it in plan, apply, `keyOf`, `removeKey` and the manual steps.
- The plan validates the `.env` destination before any mint, with the same `resolveTarget` + `protectedTarget` + `readSnapshot` rules the config file gets. Any error makes the plan manual. A forbidden place (`outsideHome`, protected) withholds the key-bearing steps (`forbiddenPlace`). Recheck before each write.

Tests:
- `config.yaml` is a symlink to `~/dotfiles/hermes.yaml`: the key lands in `~/.hermes/.env` and `~/dotfiles/.env` is never created.
- `.env` is a symlink outside home: `canApply: false`, no `<KEY>` snippet, zero CreateApp calls at the popup boundary.

H3 **The key variable is free or ours** (l1 P5-03, SEC-03, l3 P5-02, UX-04, l3 P5-05). A renamed server (`personal`) that still references `${MCP_ANYTYPE_API_KEY}` gets the newly minted key, and its old credential is overwritten. Fix: Hermes may write `MCP_ANYTYPE_API_KEY` only when both conditions hold:
- `.env` has no value for it, or (rotation only) the value's fingerprint equals `rec.keyFp`;
- no part of `config.yaml` outside `mcp_servers.anytype` mentions `MCP_ANYTYPE_API_KEY`. Check this as a string search over the parsed document with our entry deleted.

Run the check in the plan (otherwise manual with the `anytype_me` steps and a note that the variable is already used), in the apply preflight, and inside each `writeKey` attempt, so that the changed-snapshot retry cannot overwrite a concurrent edit. The final read-back (`observedInstalled`) also requires the `.env` value's fingerprint to equal the new key's. A false read-back leaves the record `pending` through the existing path; no further machinery.

Tests:
- A `personal` server referencing the variable: the plan is manual, and apply returns `conflict` with both files unchanged.
- A foreign value with no `anytype` entry: the plan is manual.
- The value changes between the snapshot and the rename: no overwrite.
- The binding is removed just before the YAML rename: `observedInstalled: false`.

H4 **`.env` edits touch only our line and leave no copies** (l1 P5-04, SEC-09 rollback part, l3 P5-03, SEC-02, SEC-07, l3 P5-08). Three failures:
- A failed YAML write rolls back the whole old `.env`, which undoes a provider token that was rotated in between.
- Every connect leaves `.env.anytype-backup` holding all provider credentials, under a name Hermes' credential guard does not cover.
- A quoted multiline value containing a line that starts with `MCP_ANYTYPE_API_KEY=` gets edited inside the other value.

Fix:
- (a) `restoreKey` works on the latest snapshot. It sets our variable back to its previous value, or removes our line if there was none. A file this attempt created may stay behind empty.
- (b) `writeFileSafe` gets a `backup: false` option, used for every `.env` write: set, restore and remove.
- (c) `envFile.ts` refuses with `unsupportedForm` when any value opens a quote that doesn't close on the same line. The plan is then manual. Use the same check for read, set and remove.

Tests:
- `OTHER=one` becomes `OTHER=two` between the writes and the YAML rename fails: `.env` ends with `OTHER=two` and no Anytype line.
- No `.env.anytype-backup` exists after connect, rollback or disconnect.
- A multiline `NOTES="…\nMCP_ANYTYPE_API_KEY=x\n…"`: the plan is manual and the file is byte-identical.

## Medium

H6 **Installer snippet: a private temp directory, and stop on failure** (SEC-05). On a shared machine a pre-existing `/tmp/anytype-cli-install.sh` runs when the download fails, because the lines run unconditionally. Fix: `d="$(mktemp -d)" && curl -fsSL <url> -o "$d/install.sh" && bash "$d/install.sh"`, then the PATH export. Test: the snippet has no fixed `/tmp/` path and chains the download and run with `&&`.

H7 **Hermes disconnect reports a leftover `.env` line** (l1 P5-10, SEC-09 cleanup part, l3 P5-06, UX-07). If the YAML entry is removed but the `.env` write fails, the user gets a clean "disconnected" while the credential line stays. Fix:
- `removeKey` returns its write result and retries once on `changed` while the fingerprint still matches.
- On failure, Hermes `remove` returns `ok: true` with a new leftover `left: 'envKey'`, with one text line: "Remove the MCP_ANYTYPE_API_KEY line from <.env path>". Revocation proceeds.

Test: make only the `.env` rename fail; the service returns `left: 'envKey'` and the disconnect view shows the line.

H8 **Manual Hermes: the permission check on `.env`** (l1 P5-07, SEC-06, l3 P5-07, UX-06). A user pastes the key into a `0644` `.env`, clicks "I've updated Hermes", and gets no tightening and no warning. Fix:
- Add `hermes` to the manual-file handling, but the checked file is the H2 `.env` (not `targetPaths[0]`), with the same ownership, symlink and inside-home rules.
- `previewTarget` still confirms the profile through the config path.

Test: a `0644` `.env` gives `fileMode: 'tightened'` and mode `0600`; another uid gives `'loose'`.

H9 **Hermes conflict copy and unknown ownership** (l1 P5-06, UX-05, plus the copy part of l1 P5-09). Three problems:

Fix:

- (c) The manual view shows the plan's note together with the steps.
- (d) For Hermes, Manage's `conflict` row offers "Set up manually" instead of Replace.
- (e) The `aiConnectHermesForeign` note adds: "If you added this entry yourself for Anytype, put the new key in MCP_ANYTYPE_API_KEY instead." This replaces l1 P5-09's record plumbing; see REJECT.

Tests:
