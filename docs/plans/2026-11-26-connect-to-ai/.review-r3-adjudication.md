# Plan review round 3 — adjudication (by the orchestrator)

Light round, 2 lenses (A = security / key lifecycle, B = consistency), critical/high only. Raw: scratchpad `reviews/plan-r3/lensA.md`, `lensB.md`. 15 findings, ~8 distinct. All ACCEPTED, with the simplest fix stated. This is the last plan round; remaining issues get caught in the phase reviews.

R3-1 **Delivery commit vs popup close** (A-02, B-01). The connect/reconnect flow outlives the popup: `flow.connect` runs in a module-level operation object, not in component state. Closing the popup (any path: Esc, Router.go closing all popups, onClose) only *requests* cancel; cleanup waits for any in-flight mint/apply IPC to settle, then: apply committed → keep the new key (record exists), finish rotation normally (revoke old); not committed → revoke the new key. Same rule for the Claude Code `add-json` timeout: before revoking, re-read the installed entry; if it carries the new key's fingerprint, it committed. Test: close before the apply reply; CLI timeout after the write.
R3-2 **Which key each fallback uses** (A-03, B-02). Manual view after a failed automatic apply shows the pending NEW key with an explicit **I've updated <App>** button → `aiConnectRecordManual` records that same key (clears pending) → only then revoke the old hash. Closing without it → revoke the new key, keep the old. Manual reconnect: show the replacement snippet first; the old key is revoked only after **I've updated <App>**. LM Studio file fallback after a successful deeplink uses the committed key looked up by the record's hash (`keyFor`). Claude Code `removedOld`: the old key stays valid; the manual view shows the OLD key (by hash) so the user can restore, plus the new one.
R3-3 **Revocation set is one rule everywhere** (A-04, B-03). Fix the §3.11 table: disconnect = `revokePending ∪ { appHash }`; releasePendingKey failure adds its hash to a machine-level `orphanHashes` list in the registry (account-scoped) retried by every check; Retry retries every outstanding hash; the record is deleted only when its set is empty. `aiConnectCheck` must not require a port when `apiListening` is false (reconcile-only mode). Test: rotation A→B with A's revoke failing → disconnect B → restart → retry with HTTP API off → both gone.
R3-4 **Claude signer before the key file** (A-01, B-04). Signed build: verify the installed extension's signer + version BEFORE writing the key file or offering Enable. Mismatch (enabled or disabled) → install the signed bundle first, key file untouched until the expected extension is observed (then write it; nextStep restart). Unsigned dev build: current behaviour. Tests: enabled and disabled wrong-signer fixtures, cancel → key file untouched.
R3-5 **Full-entry digest for owned entries** (A-05, B-05). Store `entryDigest` = sha256 of the canonical JSON (sorted keys) of the complete entry Anytype wrote (command, args, env — the wrapper env holds no key). Heal/remove/rollback only when the installed entry's digest matches. Applies to Claude Desktop config fallback; for Route A JSON/TOML entries keep the key fingerprint check (the entry contains the key) AND compare the non-key fields we own. Test: env-only edit; edit between merge and failed key-file commit.
R3-6 **Replace bound to what the user saw** (A-06). Preflight returns `foreignDigest` of the entry occupying the target; `replace` becomes `{ targetPath, foreignDigest }`; apply (and each writer retry) rechecks; changed → `conflict` and a fresh preview.
R3-7 **Codex home moves — simplify** (A-07, B-06). POC does NOT migrate. If the Codex card resolves a canonical path different from its record's: the existing row stays (Manage/Disconnect work on its stored path); the sheet shows "Codex now uses <path>" with **Connect this location**, which creates/reuses the record whose canonical path matches (reuse an existing owned record — e.g. ChatGPT's default — instead of rotating it). No automatic cleanup of the old location. Test custom → occupied default: ChatGPT's entry and key survive.
R3-8 **Re-read grant after consent** (B-07). Reconnect re-reads the live grant + expiry from `ListApps` immediately before minting (after any quit consent) and uses that; if it differs from what the sheet showed → show the new values and ask again.
R3-9 **gRPC DevTools interceptor** (A-08). Key-bearing RPCs (CreateApp, ListApps, and any other that returns keys) bypass the gRPC DevTools interceptor as well as console logging; the Phase 1 sentinel test includes an enabled interceptor.
