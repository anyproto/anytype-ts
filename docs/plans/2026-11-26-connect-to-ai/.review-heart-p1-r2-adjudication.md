## L1. Session follow-ups go only to a port the item still names — ACCEPT (lens1:R2-SEC-01, lens2:P2-01, lens3:GO2-01)

**Failing scenario.**
1. A curated session X opens on port A.
2. Anytype restarts on port B, and the item is retargeted.
3. More than 5 s later, the client sends `initialize`. `handle` refreshes the item, and the initialize succeeds on B.
4. `adoptInitialize` queues X for cleanup (`serve.go:881-884`).
5. `cleaner` sends X's DELETE to A with X's snapshot, bearer included (`serve.go:1036-1039`). Another OS user may now be listening on A.

K4 fixed this only for the shutdown DELETE (`endSession`). `renew` has the same gap: its `notifications/initialized` leg (`serve.go:980`) reuses the snapshot read before the initialize leg, and that leg can take up to 120 s.

**Fix.** Add one helper, `stillHome(ctx, snap)`. It is true when `s.conn.current(ctx)` succeeds and returns the same port and key as `snap`. This is `endSession`'s existing check, moved into the helper. Use it in two more places:
- **`cleaner`**, before every DELETE. When it is false, skip the DELETE and log "left to expire". Heart's idle timeout ends the session.
- **`renew`**, before the notification leg. When it is false, the renewal fails with `errRenewFailed`. The session it opened goes to cleanup, which then skips it.

**Tests.**
- Initialize on A, retarget to B, advance the clock past 5 s, then send a client `initialize` that succeeds on B. A receives no DELETE.
- Hold the renewal's initialize leg, retarget to B, advance past 5 s, then release. Neither the notification nor a DELETE reaches A, and the call gets the renewal-failed reply.

## L2. Only the written warning clears the reset gate — ACCEPT (lens1:R2-SEC-05, lens2:P2-02, lens3:GO2-03)

**Failing scenario.**
1. After a renewal, the warning for `tools/call` #1 is blocked in the stdout write.
2. The client sends `tools/call` #2 and then `initialize`.
3. The initialize completes. `adoptInitialize` sets `resetPending = false` (`serve.go:879`) but does not advance `resetClearedSeq`.
4. #2 is admitted and runs on the new session, before the client has seen the warning. It uses targets the client still holds from the old session.

**Fix.** Delete `s.resetPending = false` from `adoptInitialize`. The gate then clears only in the warning's `after` hook (K2).
- The cost: a `tools/call` sent right after a client's own re-initialize may get the warning once more. The warning says the call did not run, so this is safe.

**Test.** Extend K2's blocked-writer test. While the warning is held, send `tools/call` #2 and an `initialize` that heart answers.
- The fake heart receives no `tools/call` on any session until the write is released.
- #2 gets the warning.
- The next call runs on the client's session.

## L3. macOS: no ACL on the Anytype folders or the item — ACCEPT, part (lens1:R2-SEC-02, lens2:P2-03, lens3:GO2-02)

**Failing scenario.** A user shares their home with another local user in Finder (Sharing & Permissions). Finder writes inheritable allow entries, which `.anytype`, `ai-connect`, `items` and every new temp file inherit.
- The items folder still reads `0700` and the item `0600`, so every current check passes.
- But the other user can traverse the folders and read the bearer, because macOS evaluates ACL entries before the mode bits.

This is the different-user case §0.2 puts in scope. Linux is not affected:
- A POSIX ACL shows up in the group bits (the mask), which the folder rule already refuses.
- The `0700`/`0600` modes mask named entries to nothing.

**Fix.** Refuse any ACL rather than interpret it.
- **What is checked.** `.anytype`, `ai-connect`, the items folder, the item and the new temp file must carry no ACL entry at all. The item is checked through its open handle on every read. The temp file is checked before any key byte is written into it. A failure is `denied`, with the rule named ("a folder on the item path has an ACL", "the item has an ACL").
- **No cgo.** All five targets stay `CGO_ENABLED=0`. Read the ACL with `getattrlist`/`fgetattrlist` and `ATTR_CMN_EXTENDED_SECURITY` through `unix.Syscall6`; x/sys exports no wrapper. A filesec with any entry is refused.
- **Home is the exception** (L4). Home may carry deny entries only, because every Mac home has `group:everyone deny delete`.

**Rejected part.** Computing the effective grants (lens1, lens3). Refusing any entry is simpler and stricter.

**Tests** (macOS runner, scratch home):
- `chmod +a "everyone allow read,list,search,file_inherit,directory_inherit"` on `ai-connect`: Read, Write and Delete each return `denied` and touch nothing.
- An allow entry on the item alone: Read returns `denied`.
- A scratch home that carries `everyone deny delete`: every verb works.

## L4. No other user can rename a folder on the item path — ACCEPT, part (lens1:R2-SEC-03, lens2:P2-04, lens3:GO2-05)

**Failing scenarios.**
- **Unix.** The checked chain starts at `.anytype` (`file.go:67`). In a group-writable home, another user can rename `~/.anytype` aside. Two things follow:
  - A running `serve` sees confirmed absence and stays disconnected until restart.
  - In the gap between the check and the open, that user can swap in their own tree under a `key set`. On macOS, an inheritable ACL on that tree (L3) makes the new temp file readable to them.
- **Windows.** `checkDir` returns before any owner or DACL check for `.anytype` and `ai-connect` (`file_windows.go:121-123`). A user with delete-child rights on `ai-connect` can:
  - rename `items` aside, which disconnects;
  - or swap `items` and `items-dev`, which both still pass every check.

**Fix.** Extend the folder rule upwards to include home. The items folder keeps its exact rule.
- **Unix.**
  - Home must be a real directory owned by the user or root, with no group or other write bit.
  - `.anytype` and `ai-connect` keep today's rule.
  - On macOS, home may carry deny ACL entries only (L3).
- **Windows.**
  - The owner of home, `.anytype` and `ai-connect` must be the user, SYSTEM or Administrators.
  - Every allow ACE that applies to the folder itself (not inherit-only) must name one of those three.
  - Inherited entries are fine, so a standard profile passes.
- **On failure:** `denied`, with the rule named, like the other rules. On some Linux setups home is `0775` with a private group; such a home now gets that line, and the fix is `chmod g-w ~`.

**Rejected part.** Holding the verified directory handles for the whole operation (lens1, lens3). Once no other user can rename a component, reusing the path is safe against everyone in scope. The same user is out of scope.

**Tests.**
- Unix:
  - A home at `0775`: every verb returns `denied` and nothing is written.
  - A home owned by another uid (through the injectable uid): the same.
- Windows:
  - `ai-connect` with an extra `(A;;FA;;;BU)` entry: `denied`.
  - The runner's standard inherited DACLs pass.

## L5. The bearer check reads decoded strings — ACCEPT (lens1:R2-SEC-04, lens2:P2-09, lens3:GO2-11)

**Failing scenario.** A 200 body spells the bearer inside a JSON string with one ordinary letter written as `\u00XX`.
- `carriesKey` searches three byte spellings (`serve.go:745-766`) and misses it.
- The body is relayed raw: `relay` passes `result` and `error` through unchanged, and heart's full tier passes REST bodies through raw (`core/api/wrapper/full/executor.go:89`).
- The client decodes the string and the key lands in its transcript.

**Fix.** Compare decoded values, not JSON spellings.
- `carriesKey` walks the body with `json.Decoder.Token` (`UseNumber`). It reports a hit when any decoded string contains the key; member names count as strings.
- It keeps the raw-bytes check as well.
- A body the walk cannot finish is not relayed; it is reported as unconfirmed.
- `relay` and `renew` both use it unchanged.

**Test.** Put the canary, with one letter `\u`-escaped, in each of these places:
- the `result` text;
- a nested `structuredContent` value;
- a member name;
- `error.message`;
- `error.data`.

The reply is withheld every time. The test decodes the client's stdout line and asserts that no decoded string contains the canary.

## L6. `key set` writes only items the reader accepts — ACCEPT (lens1:R2-SEC-08, lens2:P2-11, lens3:GO2-13)

**Failing scenario.** The payload rule accepts a key of 1,024 visible ASCII characters.
1. A key made of `&` (or `<`, `>`) passes.
2. `json.Marshal` escapes each of those characters to six bytes, 6,144 in all (`item.go:85`).
3. `Write` replaces a working item.
4. The read-back finds more than 4 KiB, and the verb reports `unconfirmed`.
5. From then on, `key check` reports the connection absent and invalid.

The "largest item fits" test uses `k` (`item_test.go:24`), which is never escaped.

**Fix.**
- `Encode` uses an encoder with `SetEscapeHTML(false)`. The worst case, a key made of `"`, is then about 2.4 KiB.
- Validate by round trip: `Encode` returns an error unless `DecodeItem` of its own output succeeds and equals the item.
- `readPayload`'s probe (`key.go:245`) calls `Encode`. A payload that cannot round-trip is therefore exit 6, decided before the lock is taken, and `commit` can never replace an item with one the reader rejects.

**Tests.**
- The largest-item test uses the worst cases: keys of 1,024 `"`, then `&`, then `\`; a 256-character account; rev `1<<62`.
- A CLI rotation from a valid item to a key of 1,024 `&` succeeds, and `key check` reads it back.

## L7. Windows: an open reader never blocks a replacement — ACCEPT (lens1:R2-SEC-06, lens2:P2-05, lens3:GO2-04)

**Failing scenario.** `renameIn` uses `MoveFileEx(REPLACE_EXISTING)` (`file_windows.go:211`).
- The legacy rename cannot replace a file that has any open handle, even one opened with `FILE_SHARE_DELETE`. Replacing such a file needs `FILE_RENAME_POSIX_SEMANTICS`.
- So a `serve` refresh or a scanner that holds the item for 2 s makes `key set` or `retarget` exit 7.
- `TestWindowsReaderDoesNotBlockTheRename` holds such a handle across `Write` (`file_windows_test.go:59`), so it should fail on its first native run.

**Fix.**
- **One `renameIn` for both OSes: `os.Root.Rename`.** On Windows, Go uses `FileRenameInformationEx` with `REPLACE_IF_EXISTS|POSIX_SEMANTICS`, and falls back to the legacy rename where that isn't supported (FAT).
- **Keep the 2 s bounded retry** around it, for a handle that denies delete sharing. When the retry runs out, remove the temp file and exit 7 (busy, nothing written).
- **Never two key files.** If the temp file can't be removed, L8's sweep removes it.
- **Durability.** After the rename and before the receipt, open the item for write and call `FlushFileBuffers` on it. This replaces the `MOVEFILE_WRITE_THROUGH` flag, which only affects moves that copy across volumes. A failure there is `unconfirmed`.

**Tests.**
- The existing held-reader test passes on `windows-latest`.
- A reader without `FILE_SHARE_DELETE`, held for 3 s:
  - the verb exits 7 after about 2 s;
  - the old item is intact;
  - no temp file is left.

## L8. Store receipts are durable and leave one key file — ACCEPT (lens1:R2-SEC-07, lens2:P2-10, lens3:GO2-06, lens2:P2-12, lens3:GO2-07)

**Failing scenarios.**
- **Delete is not durable.** On Unix, `key delete` reports success right after the unlink (`file.go:197`). After a power loss, the item can come back.
- **New folders are not durable.** The first `key set` creates the missing folders (`file.go:75`) without syncing their parents. After a power loss, the items folder can vanish, with the item in it, even though the receipt said ok.
- **Leftover temp files survive a disconnect.** A crashed rotation leaves `<id>.<rand>.tmp`, which holds the candidate key.
  - `Delete` never sweeps, so a disconnect reports success while that file remains.
  - `sweep` also drops its read and remove errors (`file.go:176-187`).

**Fix.**
- **Unix, delete:** `Delete` fsyncs the items folder after the unlink.
  - A failure is `UnconfirmedError`.
  - `key delete` (`key.go:316-327`) maps it to exit 1 `unconfirmed`, as `commit` does. §2.9 already reconciles a lost delete.
- **Unix, new folders:** after `mkdir` creates a folder, fsync its parent. This happens before anything is written, so a failure is exit 7.
- **Delete sweeps too:** `Delete` sweeps this id's temp files under the lock before it removes the item, as `Write` does.
  - `sweep` returns its errors, except not-exist.
  - On Windows, a busy file gets the same 2 s retry.
  - A leftover that can't be removed makes the verb exit 7, with the item untouched.
- **The rule:** after a successful verb, the only file holding a key for this id is its item, or no file at all after a delete.

**Tests.**
- A leftover from a crashed rotation, followed by `key delete`: no file under the scratch home contains the canary.
- A stage hook that fails the folder fsync after the unlink: exit 1 `unconfirmed`, and the item is gone.
- A stage hook that fails the sweep: exit 7, and the item is unchanged.

## L9. Shutdown covers the first read and hands off late sessions — ACCEPT (lens3:GO2-08, lens2:P2-06 part, lens2:P2-07)

**Failing scenarios.**
- **A stalled first read blocks signals.** `Serve` calls `conn.start` before it reaches its select (`serve.go:176`), and `File.Read` ignores its context. If that first read stalls, for example on an unavailable network home, `NotifyContext` catches SIGTERM and nothing acts on it.
- **A late session id is dropped.** On SIGTERM, shutdown cancels the run and closes the cleanup queue at once (`serve.go:231-232`). A worker whose `initialize` already received heart's `Mcp-Session-Id` header then calls `dropSession`, which returns silently because the queue is closed (`serve.go:1011`). The session holds one of heart's 8 per-key slots (`core/api/server/mcp.go:47`) until it expires idle.

**Fix.**
- **First read.** Run `conn.start` in a goroutine, and have `Serve` select on it and on `ctx`. On a signal, `Serve` returns, and `main`'s `os.Exit` ends the stuck read. The reader and the workers start only after `start` returns, because they must never run on an empty snapshot.
- **Late sessions.** Track the worker goroutines with their own WaitGroup. Shutdown runs `stopRun`, waits for the workers within the deadline, and only then calls `closeDrop`. It cannot wait on `accepted` instead, because queued calls never finish after `stopRun`.

**Tests.**
- A store double whose first read blocks, then a cancelled context: `Serve` returns within the deadline.
- SIGTERM after heart has sent an initialize's headers but before its body: the DELETE reaches heart before exit, since the item still names that port (L1).

## REJECT

- **lens1:R2-SEC-09, part: a key in a logged method name.** The MCP client program chooses the method; neither the model nor heart does. A method can hold the key only if that client already holds it, and stderr goes back to the same host. K3 already strips control characters and caps the line.
- **lens2:P2-08 / lens3:GO2-09, main part: cancelling a local ping.** MCP lets a receiver ignore a cancel for a request whose processing has finished, and clients must handle a reply that crosses a cancel. A local reply (ping, busy, a refusal) is finished when it is queued. K5's rule covers accepted requests. (The test-spelling part is in L10.)
- **lens2:P2-06, part: EOF is seen late while the reader is blocked on a local reply and stdout is stalled.** This is bounded:
  - The 30 s stall watchdog breaks stdout, and shutdown follows within the deadline.
  - A host that has stopped reading stdout is not waiting for anything it could lose.
- **lens3:GO2-10: cancelled renewal waiters hold workers.** This costs capacity only:
  - Waiters are bounded by the leader's 120 s exchange timeout and are released at once when shutdown cancels.
  - A cancelled waiter writes nothing.
  - It is not worth new concurrency code in a capped round.
- **Partial rejections inside accepted themes:**
  - L3: computing effective ACL grants.
  - L4: holding verified directory handles for the whole operation.
